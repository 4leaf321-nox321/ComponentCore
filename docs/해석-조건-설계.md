# 해석 조건 설계 — 점 · 선 · 면에 조건을 붙여 넘긴다

> 작성 2026-09-23. 이 플랫폼이 **어디까지 하고** 무엇을 파일로 넘기는지 정한다.
> 받는 쪽 계약은 [SimEngBay/docs/해석-연동-계획.md](../../SimEngBay/docs/해석-연동-계획.md)
> 「0단계 — CAD 계약」 이다. 그쪽이 기다리는 것을 이쪽이 내주는 것이 이 문서의 목적이다.

## 0. 경계 — 누가 무엇을 하나

```
CompCore  — CAD 를 DOE 로 만드는 데 특화              해석 플랫폼들
형상(레시피) · 영역 나누기 · 조건 정의                 SimEngBay (Ansys Mechanical)
DOE 로 설계점 N 벌                                   그 밖의 시뮬레이션 플랫폼
  │                                                  │
  └─ 한 폴더 ──▶  STEP · topology.json ·  ───────────▶│ 제 방식으로 읽어
                 conditions.json · point 메타         │ 메시 · BC · 솔브 · 결과 화면
                                                      │
       물성을 골라 온다 ◀──── PAT ──── MatNexus (:8010)
```

**이 플랫폼은 메시도 솔브도 하지 않고, 결과도 받지 않는다**(2026-09-23 결정). 하는 일은
**CAD 를 DOE 로 만드는 것**과, 그 형상 위의 조건을 **솔버를 모르는 중립 JSON** 으로 함께
내보내는 것까지다.

- **결과는 해석 플랫폼의 화면에서 본다.** 설계점을 고르는 일(파레토 · 필터)도 거기서 한다 —
  그래서 이쪽의 `DoePoint.metrics` · `/filter` · `/tradeoff` 는 **채워질 일이 없다**(8장).
- **받는 쪽이 하나가 아니다.** 지금은 SimEngBay(Ansys Mechanical)지만 다른 시뮬레이션
  플랫폼과도 잇는다. 그래서 내보내는 것은 **어느 솔버의 말도 아닌 중립 표현**이어야 하고,
  솔버별 매핑(4장)은 **받는 쪽의 표**다 — 우리가 들고 있지 않는다.
- 그러므로 폴더 하나가 **자기 설명적**이어야 한다: 형상(STEP) · 어디가 어디인가(topology) ·
  무엇을 할 것인가(conditions) · **이 점이 무엇인가**(설계점 메타).

## 1. 함정 둘, 그리고 그 답

### ① 면 번호는 설계점마다 달라진다

조건을 「7번 면」 으로 저장하면 DOE 가 두께를 3 → 10 으로 훑는 순간 다른 면을 가리킨다.
**조건은 셀렉터(기하 조건)로 저장하고 설계점마다 다시 푼다.** 이 플랫폼은 형상을 결과가
아니라 **레시피**로 들고 있어 이것이 자연스럽다 — `recipe_find` 가 이미 그 언어다.

### ② STEP 은 이름표를 못 나른다

AP242 에 group 이 있지만 Workbench 가 읽어 준다고 믿을 수 없다. 세 겹으로 막는다:

1. **면을 미리 쪼갠다**(`divide_face`) — 하중을 거는 자리가 *그 자체로 하나의 면*이 되게 한다.
   그러면 받는 쪽은 그 면 하나만 집으면 된다. **이것이 DIVIDE FACE 가 있어야 하는 진짜 이유다.**
2. **좌표 지문을 함께 보낸다** — 면 중심 · 법선 · 넓이, 엣지 중점 · 접선 · 길이, 점 좌표.
3. **못 찾으면 시끄럽게 실패한다** — 조용히 0개를 집으면 하중 없는 해석이 끝까지 돌아 버린다.
   SimEngBay 의 `region_unresolved` 즉시 실패와 짝을 이룬다.

## 2. 형상 층 — 고르기와 나누기

### 있는 것

`recipe_find`([core/recipe/query.py](../backend/app/core/recipe/query.py))가 이미 답을 준다:

| 물음 | 칸 |
| --- | --- |
| 무엇을 | `what=edges\|faces`, `kind`(line · circle · plane · cylinder) |
| 어디의 | `role`(top · bottom · side · step · underside) · `of_face_role` · `axis` |
| 어느 크기 | `radius` · `min_length` · `max_length` |
| 어디 가까이 | `near=[x,y,z]` (가까운 순) · `limit` |
| 답 | 면: `center` · `normal` · `area` · `radius` · `axis` / 엣지: `midpoint` · `length` · `axis` |

**이 답의 모양이 곧 `topology.json` 의 모양이다**(centroid · normal · area) — 새로 만들 것이
아니라 이미 있는 것을 내보내면 된다. SimEngBay 쪽 문서도 그렇게 적어 두었다.

### 더할 것 ①: 점(vertex) 고르기

지금은 엣지 · 면뿐이다. `_vertex_row`(좌표 + 붙은 엣지 수)를 더하고 `what=vertices` 를 연다.
원격 하중의 부착점 · 측정점에 필요하다. 작은 일이다.

### 더할 것 ②: `divide_face` 노드

**실측(2026-09-23)**: `OCP.BRepFeat_SplitShape` 로 상자(60×40×10) 윗면에 Ø16 원을 찍었다.

```
나누기 전 6면 · 윗면 2400.0 mm²
나눈 뒤   7면 · 윗면 조각 [201.1, 2198.9]     (π·8² = 201.06)
부피 24000.0 → 24000.0 (보존)
```

번들 안의 build123d 가 OCP 를 끌고 오므로 **의존성을 하나도 더하지 않는다.**

노드 모양(초안):

```jsonc
{ "op": "divide_face",
  "on":   { "role": "top" },              // 나눌 면 — FaceSelect 그대로
  "with": { "shape": "circle", "radius": 8, "at": [0, 0] },   // 또는 rect · sketch · plane
  "tag":  "패드" }                        // 생긴 안쪽 면에 붙는 이름표
```

- `tag` 는 **면의 이름이 아니라 셀렉터의 씨앗**이다. 뒤의 노드(필렛 · 패턴)를 지나며 면이 또
  갈라질 수 있으므로, 내보낼 때 `{"tag": "패드"}` 를 **다시 풀어** 그때의 면 전부를 모은다.
  풀린 결과가 0개면 실패다 — 위 ③.
- 자르는 도형은 **대상 면의 평면 위**에 놓는다. 곡면 분할은 1차에서 다루지 않는다(원통면에
  띠를 두르는 일은 그 다음).

## 3. 조건 모델 — 솔버를 모르는 층

파일 하나(`conditions.json`)가 스터디 · 버전에 붙는다. **이름표(named_selections)가 조건이
붙는 유일한 창구**다.

```jsonc
{
  "schema_version": 1,
  "units": { "length": "mm", "mass": "kg", "time": "s", "force": "N", "temperature": "C" },

  "named_selections": [
    { "name": "고정면",   "entity": "face",   "select": { "role": "bottom" } },
    { "name": "하중영역", "entity": "face",   "select": { "tag": "패드" } },
    { "name": "볼트구멍", "entity": "face",   "select": { "kind": "cylinder", "radius": 4.25 } },
    { "name": "측정점",   "entity": "vertex", "select": { "near": [60, 0, 12] } }
  ],

  "materials": [
    // apply_to 는 topology.json 의 bodies[].name — 5장. "전체" 는 모든 바디.
    { "apply_to": "전체",
      "ref": { "source": "matnexus", "code": "M-000241", "name": "AL6061-T6",
               "fetched_at": "2026-09-23T10:00:00+09:00" },
      "snapshot": { "E_MPa": 68900, "nu": 0.33, "density_kg_m3": 2700,
                    "at_temperature_C": 22 } }        // 자세한 것은 6장
  ],

  "contacts": [
    { "name": "지그-부품", "source": "지그윗면", "target": "부품바닥",
      "type": "frictional", "friction": 0.15,
      "formulation": "augmented_lagrange", "behavior": "asymmetric",
      "pinball_mm": 0.5, "interface_treatment": "adjust_to_touch" }
  ],

  "constraints": [
    { "name": "바닥고정", "type": "fixed_support", "on": "고정면" },
    { "name": "옆면",     "type": "displacement",  "on": "측면",
      "cs": "global", "x": 0, "y": null, "z": null }      // null = 자유
  ],

  "loads": [
    { "name": "누름", "type": "pressure", "on": "하중영역", "magnitude_MPa": 2.5, "direction": "normal" },
    { "name": "볼트", "type": "bolt_pretension", "on": "볼트구멍", "preload_N": 8000 },
    { "name": "중력", "type": "standard_earth_gravity", "direction": [0, 0, -1] }
  ],

  "initial": [
    { "type": "environment_temperature", "value_C": 22 },
    { "type": "velocity", "on": "낙하물", "vector_mm_s": [0, 0, -3000] },
    { "type": "prestress", "from_step": "정적" }
  ],

  "analysis": {
    "type": "modal",                 // static | modal | harmonic | explicit
    "prestressed": true, "modes": 6, "frequency_range_hz": [0, 2000],
    "large_deflection": false
  },

  "mesh_hints": [
    { "on": "하중영역", "element_size_mm": 1.0 },
    { "on": "볼트구멍", "type": "inflation", "layers": 3 },
    { "on": "전체", "method": "tetrahedra", "order": "quadratic", "defeature_size_mm": 0.3 }
  ]
}
```

**단위는 파일에 박는다.** 이 플랫폼은 mm · MPa · kg 로 적고, SimEngBay 의 `MaterialSpec` 은
GPa · kg/m³ 로 받는다 — **환산은 내보내는 쪽(여기)이 한다.** 받는 쪽이 추측하지 않게.

### 조건도 변수로 훑는다 — CAD 치수와 **같은 자리**

「두께 6 · 8 · 10 을 압력 2 · 3 MPa 로」 처럼 **조건도 설계점마다 달라야 한다.** 그래서 조건의
숫자 칸에도 레시피와 똑같이 `"=식"` 을 쓴다:

```jsonc
"params": { "두께": 8, "압력": 2.5, "볼트_토크계수": 0.2 },   // 레시피의 params 그대로

"loads": [
  { "name": "누름", "type": "pressure", "on": "하중영역",
    "magnitude_MPa": "=압력" },                      // ← 변수
  { "name": "볼트", "type": "bolt_pretension", "on": "볼트구멍",
    "preload_N": "=볼트_토크계수 * 8000" },           // ← 식도 된다
]
```

**새 장치를 만들지 않는다.** `core/recipe/params.py` 의 `resolve()` 는 dict · list 를 훑어
`"=" ` 로 시작하는 글자를 숫자로 바꾼다 — 레시피에 쓰던 그 함수를 조건에 그대로 쓴다.
그래서:

- **DOE 는 하나도 안 바뀐다.** 지금도 설계점마다 `params` 를 덮어써 레시피를 다시 푼다.
  조건은 내보낼 때 **같은 `params` 로** 한 번 더 풀면 된다.
- **형상에 안 쓰이는 변수를 둬도 된다**(`압력`). 레시피 평가는 안 쓰는 변수를 무시한다.
  DOE 폼의 변수 목록에 그대로 나오므로 범위를 주는 길도 이미 있다.
- **조건이 치수를 따라가게 할 수 있다** — `"magnitude_N": "=두께 * 120"`. 한 변수를 훑으면
  형상과 하중이 함께 움직인다.
- **풀린 값이 말이 안 되면 그 점만 실패한다**(음수 압력 · 마찰계수 1.2). DOE 가 이미 「실패한
  점에서 멈추지 않는다」 로 도는 규칙 그대로, 사유를 줄에 적고 다음으로 간다.

#### 형상이 같고 조건만 다른 점들

이 방식의 부작용 하나: `압력` 만 훑으면 **STEP 이 전부 같다.** 그것을 받는 쪽이 알아야 메시를
다시 만들지 않는다 — 설계점 메타의 `recipe_digest`(5장)가 그 열쇠다. 같은 다이제스트면 같은
형상이니 메시를 재사용하고 하중만 바꿔 다시 푼다.

우리 쪽에서도 같은 형상을 여러 번 만들 이유가 없다. 다만 **파일은 점마다 그대로 쓴다** —
폴더 하나가 자기 설명적이어야 한다는 원칙(0장)이 「점 하나 = 파일 한 벌」 을 요구하고, STEP
하나는 수십 MB 가 아니다. 무거워지면 그때 같은 다이제스트끼리 심볼릭 링크로 묶는다.

## 4. ANSYS Mechanical 매핑

| 중립 | Mechanical | 비고 |
| --- | --- | --- |
| `fixed_support` · `displacement` · `frictionless` · `cylindrical` | 같은 이름의 Support | `null` = Free |
| `pressure`(normal) · `force` · `moment` · `bearing` | Pressure · Force · Moment · Bearing Load | Force 는 벡터 · 성분 둘 다 |
| `bolt_pretension` | Bolt Pretension | Preload(N) 또는 Adjustment(mm). **볼트 원통면**에 건다 |
| `standard_earth_gravity` · `acceleration` · `rotational_velocity` | 같은 이름 | 중력은 가속도의 반대 부호 |
| `bonded` · `no_separation` · `frictional` · `frictionless` · `rough` | Contact Type 그대로 | `formulation=MPC` 는 Bonded 에서만 값어치 |
| `environment_temperature` | Analysis Settings ▸ Environment Temperature | 열응력의 기준 |
| `prestress` | Static → Modal 의 Pre-Stress 링크 | **볼트를 조인 상태의 공진** — 이 플랫폼의 주 용도 |
| `velocity`(초기) | Explicit/Transient ▸ Initial Conditions | 낙하 · 충격 |

다른 솔버(Abaqus · CalculiX)는 이 표를 한 장 더 두면 된다 — 조건 모델은 그대로다.

## 5. 무엇을 파일로 내보내나

DOE 폴더 한 벌(`<이름>-<id8>/`)에 이렇게 얹는다:

| 파일 | 내용 | 상태 |
| --- | --- | --- |
| `points/pNNNN.step` | 형상 | 있다 |
| `points/pNNNN.json` | **이 점의 모든 것** — 변수 값 · 영역 · 바디 · 풀린 조건 | 있다 |
| `conditions.json` | 3장의 조건 모델 — 스터디 공통, 셀렉터 기준 | 3단계 |
| `study.json` | 기준 레시피 · 인자 정의 · 시드 | 있다 |
| `manifest.csv` | 점 · 상태 · 바꾼 변수 · 파일 · `topology` · `unresolved` | 있다 |

**받는 쪽은 이 폴더만 보고 해석을 세울 수 있어야 한다.** 우리에게 되물을 API 가 없다는 뜻이다 —
연계할 플랫폼이 하나가 아니고, 그중에는 우리 API 를 부를 수 없는 자리도 있다.

### 설계점 메타 — 「이 점이 무엇인가」

점 파일(`points/pNNNN.json`)에 `point` 블록으로 함께 싣는다. **점 하나 = 파일 하나**다 —
영역과 조건은 늘 짝으로 읽히므로 나누면 「하나는 있고 하나는 없는」 상태가 생길 자리만 는다
(2026-09-24 에 `topology.json` · `conditions.json` 둘을 합쳤다).

```jsonc
{ "units": "mm",
  "point": {
    "number": 7,
    "study": { "id": "3f9a21…", "name": "브래킷_튜닝", "seed": 1, "method": "lhs" },
    "params": { "두께": 8.0, "스팬": 120.0 },        // 이 점에서 바꾼 변수
    "recipe_digest": "sha256:…",                    // 같은 형상인지 되짚는 열쇠
    "step_file": "points/p0007.step",
    "created_at": "2026-09-23T10:00:00+09:00"
  },
  "bodies": [ … ], "regions": { … }, "unresolved": [] }
```

- **`params` 가 핵심이다.** 결과를 우리가 받지 않으므로, 해석 쪽이 「이 결과가 두께 8 짜리」
  라는 것을 **파일만 보고** 알아야 한다. `manifest.csv` 에도 같은 값이 있지만, 점 파일 하나가
  자기 이야기를 다 하는 편이 낫다 — CSV 를 열지 않고 점 하나만 집어 가는 길이 흔하다.
- **설계점마다 topology 를 따로 낸다.** 같은 이름표라도 좌표가 점마다 다르기 때문이다.
- 이름표가 하나라도 안 풀리면 `unresolved` 에 이름이 남고 manifest 에 적힌다. 그 점에서
  멈추지 않는다 — DOE 가 이미 「실패한 점에서 멈추지 않는다」 로 도는 것과 같은 규칙.
- **되돌아오는 길은 없다**(0장). 결과는 해석 플랫폼이 들고 거기서 본다.

### 어느 바디에 붙이나 — 화면 (2026-09-24)

칸은 `Material.apply_to` 로 처음부터 있었지만 **고를 길이 없었다** — 늘 「전체」 였다. 조립을
훑어도 판과 기둥에 다른 재료를 줄 수 없었다는 뜻이다.

- `POST /cad/recipe/bodies` 가 고를 것을 준다(`topology.bodies` 그대로 — 이름 · 부피 ·
  무게중심 · `step_product`). **화면이 메시의 면에서 지어내지 않는다**: 내보낼 때 쓰는
  이름은 `topology.bodies` 가 정하므로, 두 곳이 어긋나면 사람이 고른 바디가 폴더에 없는
  이름이 된다.
- 조건 화면의 물성 줄마다 「붙일 자리」. **바디가 하나면 칸을 안 그린다** — 누를 수 없는
  줄은 없느니만 못하다. 부피를 함께 보여 이름이 비슷할 때 가른다.
- **없는 바디를 가리키면 막는다**(`parse(raw, bodies)`). 작업 저장에도 DOE 만들기에도 건다 —
  물성이 없는 바디에 붙으면 해석이 그 바디를 **맨몸으로** 푼다. 값이 안 나오는 게 아니라
  기본값으로 풀려 그럴듯한 답이 나온다. 이름표를 가리킬 때와 같은 까닭이다.
  도면을 못 만들면 검사를 건너뛴다 — 검사 하나 때문에 조건 저장이 막히면 사람이 고치던
  것을 잃는다.

`converted` 는 **출처가 달라도 한 모양**이다. 등록 재료는 밀도 · 푸아송비가 payload 의 칸으로
오고 문헌은 `values[]` 안에 줄로 오는데, 그대로 두면 받는 쪽이 출처에 따라 두 군데를 봐야
한다 — 못 채웠으면 목록에서 끌어올린다.

### 할당은 어디를 가리키나 — `bodies`

물성은 **파트마다** 붙는다(`materials[].apply_to`). 그런데 그 「파트」 를 받는 쪽이 어떻게
알아보나? 면에 쓴 방법을 솔리드에도 그대로 쓴다 — **좌표 지문**이다.

**실측(2026-09-23)**: 이름표 붙은 조립(`부품` + `지그판`)을 `export_step` 으로 써 봤다.

| | 결과 |
| --- | --- |
| 조립 구조 | **남는다** — `PRODUCT(…)` 셋 + `NEXT_ASSEMBLY_USAGE_OCCURRENCE` 둘 |
| ASCII 이름(`part_main` · `jig_plate`) | **그대로 읽힌다** |
| 한글 이름(`부품` · `지그판`) | **깨진다** — 파일에 UTF-8 바이트가 아예 없고 `ì¡°ë¦½` 꼴로 망가져 되살릴 수 없었다 |

그래서 **STEP 의 PRODUCT 이름에만 기대지 않는다.** `topology.json` 에 `bodies` 를 함께 싣는다:

```jsonc
{ "units": "mm",
  "bodies": [
    { "name": "지그판", "step_product": "jig_plate",
      "volume": 30000.0, "centroid": [0, 0, -8], "bbox": [[-30,-25,-13],[30,25,-3]] },
    { "name": "부품",   "step_product": "part_main",
      "volume": 7200.0,  "centroid": [0, 0, 0],  "bbox": [[-20,-15,-3],[20,15,3]] }
  ],
  "regions": { "고정면": [ … ], "하중영역": [ … ] } }
```

- **`name`(한글 — 사람의 말)과 `step_product`(ASCII — 기계의 말)를 함께 적는다.** JSON 은
  UTF-8 이라 한글이 안전하고, STEP 에는 ASCII 만 내보낸다. 내보낼 때 이름표에서 슬러그를
  만들어 붙이고(`지그판` → `jig_plate`) 그 대응을 이 파일이 들고 간다.
- 받는 쪽은 **부피 · 무게중심으로 바디를 짝짓는다** — 면을 centroid · 법선 · 면적으로 짝짓는
  것과 같은 방식이라 규칙이 하나다. 이름이 깨져도, STEP 임포트가 바디 순서를 바꿔도 견딘다.
- `materials[].apply_to` 와 `mesh_hints[].on`(바디 단위일 때)이 이 `bodies[].name` 을 가리킨다.
  못 찾으면 이름표와 같은 규칙으로 **즉시 실패**한다.

## 6. 물성 — MatNexus 에서 골라 온다

**정본은 [MatNexus](file:///mnt/f/data/0_Program/66_MatNexus)**(물성 관리 플랫폼, 포트 8010,
같은 StandardPlatform 계열 — PAT 이 있다). 이 플랫폼은 물성을 **만들지 않고 고른다.**

### MatNexus 가 이미 주는 것 (2026-09-23 소스 확인)

| 무엇 | 어디 |
| --- | --- |
| 재료 목록 · 검색 | `GET /api/materials` — `q` · `name` · `alias` · `code` · `family` · `category` · **`workspace`**(부서 slug), 쪽 넘김. ~~`scope`~~ 는 **2026-09-24 권한 개편으로 사라졌다** |
| 재료 하나 | `GET /api/materials/{id}` → `code`(**`M-000123`, 불변**) · `record_name` · `alias` · `family/category/grade` · **`density`** · **`poisson_ratio`** · `declared_properties[]` |
| 물성 항목 사전 | `GET /api/materials/property-items` (MaterialTwin 키 — `mechanical.youngs_modulus` · `physical.density` · `thermal.conductivity` …) |
| 값의 출처 | `GET /api/materials/{id}/property-sources` — 실측인지 문헌인지 |
| 통째로 | `GET /api/materials/export` — **값은 SI 그대로** |

- **`code` 가 우리가 붙잡을 손잡이다.** 이름은 기준정보 개명에 따라 바뀌지만 `code` 는 안 바뀐다.
- **탄성계수는 `declared_properties` 에 있다** — 시험이 주지 않는 값(핸드북 · 규격 · 밀시트)이라
  컬럼이 아니라 목록이다. 밀도 · 푸아송비만 컬럼이다.
- **온도 의존 표가 있을 수 있다.** MatNexus 주석의 실례: 강판 탄성계수 상온 206 GPa → 400 °C
  170 GPa. 그러므로 「값 하나」 로 가정하면 안 된다.
- 솔버 덱 렌더러는 **LS-DYNA 만 있다**(`matcore/export/dyna.py` — `dyna_elastic` · `dyna_thermal`).
  ANSYS/MAPDL · MatML 렌더러는 없다.

### 그래서 이렇게 한다 — **통째로 받아 통째로 넘긴다** (2026-09-23 결정)

**이 플랫폼은 물성을 해석하지 않는다.** 재료를 고르면 그 재료에 달린 물성을 **있는 그대로**
받아 저장하고, 화면에는 구조를 그대로 펼쳐 보여 주고, 내보낼 때 그대로 싣는다.
**「어느 것이 영률인가」 는 시뮬레이션 쪽(SimEngBay)이 정한다** — 그쪽이 솔버를 알기 때문이다.

```jsonc
{ "apply_to": "전체",
  "ref": { "source": "matnexus", "code": "M-000123", "material_id": "…uuid…",
           "name": "SPCC 1.2t", "fetched_at": "2026-09-23T10:00:00+09:00" },
  "payload": {                       // MatNexus 응답 그대로. 우리가 고치지 않는다.
    "code": "M-000123", "record_name": "SPCC 1.2t",
    "family": "강판", "category": "냉연", "grade": "SPCC",
    "density": 7850.0, "density_unit": "kg/m^3",
    "poisson_ratio": 0.30,
    "declared_properties": [
      { "item": "탄성계수", "si_unit": "Pa", "input_unit": "GPa", "scale": null,
        "points": [ { "temperature_C": 22, "value_si": 2.06e11 },
                    { "temperature_C": 400, "value_si": 1.70e11 } ] },
      { "item": "열전도율", "si_unit": "W/(m·K)", "points": [ … ] }
    ] } }
```

- **값과 단위를 떼지 않는다.** MatNexus 가 `si_unit` 을 줄에 붙여 주는 이유가 그쪽 주석에 적혀
  있다 — SI 값만 받은 쪽이 단위를 짐작하다가 **밀도에서 10¹² 배로 틀린 적이 있다.** 통째로
  나르면 그 사고가 구조적으로 불가능하다.
- **항목 이름을 우리가 정규화하지 않는다.** 항목 목록은 **부서가 정한다**(MatNexus D7). 오늘
  「탄성계수」 인 것이 내일 다른 이름일 수 있고, 그 매핑은 솔버 덱을 만드는 쪽의 일이다.
- **온도 표는 줄 안에 있다.** 한 항목이 여러 줄이 아니라, 한 줄이 `points[]`(온도 오름차순)를
  든다. 경도처럼 척도로 재는 물성은 `scale`(HV · HB · HRC)이 값의 일부다 — 단위가 아니라서
  환산식이 없다. **그대로 나르면 이것도 저절로 지켜진다.**

### 창고가 둘이다 — 등록 재료와 **문헌 물성** (2026-09-24)

| | 등록 재료 `/api/materials` | 문헌 `/api/catalog` |
| --- | --- | --- |
| 무엇 | 우리 조직이 시험하고 등록한 것 | 데이터시트 · 논문에서 모은 것 |
| 몇 건 | 135 | **2663** (탄성계수를 가진 것만 1025) |
| 값의 모양 | `declared_properties[].points[].value_si` (온도 표) | `values[]` 에 `property_key` · `value_num` · `unit` 한 줄씩 |
| 분류 | 쪽(族) · 갈래 | 하위계(packaging · pcb · housing …) · 갈래(ceramic · polymer …) |
| 덤 | 부서 · 시료 수 | **조건**(`{test: "85°C/85%RH 168hr"}`) · **등급**(tier 1~4) · 출처 URL |
| 못 닿으면 | 올려 둔 사본으로 | **빈손** — 문헌은 사본이 없다 |

**값의 모양이 다른데 payload 를 한 모양으로 고치지 않는다**(감사의 정본이다). 한 모양이
필요한 쪽은 `converted` 를 본다 — `converted_material` 이 둘을 받아 하나로 내놓는다.

문헌 값은 **조건과 등급이 값의 일부**다. 「85°C/85%RH 168hr」 에서 잰 흡습률을 상온 값으로
쓰면 틀리고, tier 4 를 tier 1 인 줄 알고 쓰면 틀린다 — 그래서 `converted` 에도 화면에도
함께 싣는다. `property_key`(`mechanical.youngs_modulus`)도 나른다: **기계가 읽을 이름**이라,
받는 쪽이 「어느 것이 영률인가」 를 이름으로 풀 수 있다.

**목록에는 값을 안 싣는다.** 재료 하나에 값이 중앙값 6개지만 **최대 786개(2.6 MB)** 라,
2663건을 값째로 끌면 한 번에 수십 MB다. 고른 뒤 그 재료만 받고, 그때 **대표값만**
담는다(`representative`, 중앙값 4개). 대표가 하나도 없으면 전부 담는다.

**단위는 68종**이 나온다(우리 표는 그때 25종이었다). 86% 를 환산하고, 10% 는 일부러
안 한다(전기 · 자기 · 몰 · 경도 척도 — 차원이 우리 넷에 안 담긴다), 3% 는 모른다.
**모르는 것은 조용히 지나가지 않는다** — `unconverted` 에 이름이 남는다.

### 「어느 것이 영률인가」 — **열쇠 하나로** (2026-09-24)

걱정은 「문헌은 용어가 흩어져 있을 것」 이었는데 **재 보니 반대였다**:

| | 기계가 읽을 이름 |
| --- | --- |
| 문헌 `/api/catalog` | ✅ `property_key`(`mechanical.youngs_modulus`) — 2140개 값이 **한 열쇠**에 모여 있다. 269종은 동의어가 아니라 서로 다른 물리량이다 |
| 등록 재료 `/api/materials` | ❌ **한글 라벨뿐**(`item: "탄성계수"`). 열쇠 칸이 없다 |

MatNexus 가 상류에서 용어를 이미 정규화했고, **사전에 우리 사내 항목 이름까지 걸어 두었다**
(`/api/catalog/properties/dictionary` 의 `internal_items`). 등록 재료의 여덟 항목이 모두
덮인다 — 우리가 한글 표를 따로 만들면 그쪽이 항목을 하나 더하는 날 우리만 모른다.

그래서 **그 사전으로 등록 쪽에도 같은 열쇠를 붙인다.** 결과: 받는 쪽은 출처를 가리지 않고
한 규칙으로 읽는다.

```jsonc
"converted": {
  "density": 2.68e-09, "density_unit": "tonne/mm3", "density_key": "physical.density",
  "poisson_ratio": 0.33,                            "poisson_key": "mechanical.poisson_ratio",
  "properties": [{ "item": "탄성계수", "key": "mechanical.youngs_modulus",
                   "unit": "MPa", "points": [{ "value": 70300 }] }]
}
```

**밀도 · 푸아송비는 등록 쪽에서 컬럼으로 온다**(줄이 아니라) — 그래서 위에 따로 올리고
열쇠도 같이 붙인다. 받는 쪽이 한 곳만 보면 되게.

열쇠는 **덤이다.** 사전을 못 가져와도 값은 그대로 나가고 열쇠만 없다. 그리고 **코어는
사전을 가져오지 않는다** — 네트워크는 바깥 층의 일이다(아키텍처 시험이 지킨다. 실제로
`core/conditions.py` 에 넣었다가 잡혔다).

### 해석에 바로 쓸 수 있나

문헌 2663건 중 **탄성계수를 가진 것은 1025건**이다 — 고른 재료에 그것이 없을 수 있다는
뜻이다. 없으면 해석이 **기본값(구조용 강)으로 풀고**, 그 사실은 고유진동수가 틀린 뒤에야
드러난다. 그래서 고를 때 말한다(`converted.missing_structural`).

**모르는 것과 없는 것은 가른다**: 목록 한 줄에는 값이 아예 안 딸려 오므로 거기서는 이 칸이
안 나온다 — 「다 빠졌다」 고 하면 거짓말이다(아직 안 봤을 뿐이다).

값이 여럿일 때(탄성계수를 가진 1025건 중 334건)는 **대표값**이 있다 — 대표 표시가 없는
재료는 0건이었다(실측). 나머지는 조건이 다른 것이다(온도 · 층수 · 방향).

### 물성 탐색기 (화면)

조건 편집기와 「부품에서 지그 생성」 옵션 옆에서 부른다.

```
[물성 고르기]  검색: SPCC        family: 강판 ▾   범위: 전체 ▾
 ┌ M-000123  SPCC 1.2t        강판 · 냉연 · SPCC     전역
 │ M-000241  AL6061-T6        알루미늄 · 압출        내 작업공간
 └ …                                              (쪽 넘김)

고르면 — 받아 온 것을 **그대로 펼친다**
  밀도            7850 kg/m^3
  푸아송비        0.30
  탄성계수        22 °C 206 GPa · 400 °C 170 GPa      (출처: 문헌)
  열전도율        …
  경도            HV 120                              (척도 — 환산 안 함)
  [이 물성을 쓴다]   [질량 계산에 쓸 줄 고르기 ▾]
```

- **구조를 그대로 보여 준다.** 우리가 아는 항목만 골라 보여 주면, MatNexus 에 있는데 화면에
  없는 물성이 생기고 사람은 그것이 없는 줄 안다.
- **브라우저가 MatNexus 를 직접 부르지 않는다.** 이쪽 서버가 PAT 을 들고 중계한다
  (`app/modules/materials/routes.py` → `app/shared/clients/matnexus.py`). 토큰이 화면에 나가지
  않고, CORS · 망 분리도 서버 쪽 문제로 남는다.
- **권한은 MatNexus 의 것을 따른다**(`scope=all|mine|global` · 작업공간). 우리가 다시 판단하지
  않는다.
- 캐시 표 `material_snapshots`(code · fetched_at · **원본 JSON 그대로**) — 같은 재료를 여러
  작업이 쓰고, MatNexus 가 잠깐 없어도 화면이 뜬다. **정규화한 열은 두지 않는다.**
- 못 닿거나 아직 등록 안 된 재료는 **손입력**(`source: "손입력"`) — 그때는 사람이 적은 것이
  곧 payload 다.

### 다만 이 플랫폼이 스스로 계산하는 두 자리

질량 · 무게중심 · 관성(치수표)은 **밀도**가, 보 1차 공진 가늠값은 **탄성계수**가 있어야 나온다.
여기서만 payload 를 들여다본다. 규칙:

1. 기본 열쇠(`density` 컬럼, 항목 이름 `탄성계수`)로 먼저 찾는다.
2. **못 찾거나 `si_unit` 이 비어 있으면 계산하지 않는다.** 짐작하지 않고 화면에 이유를 적는다
   — 「밀도를 못 찾아 질량을 내지 않았습니다(재료 M-000123)」. 틀린 질량은 맞는 침묵보다 나쁘다.
3. 사람이 화면에서 **어느 줄을 쓸지 직접 지정**할 수 있다(항목 이름이 부서마다 다르므로).
4. 온도 표면 상온(가장 낮은 점, 또는 사람이 고른 온도)을 쓰고 **어느 점을 썼는지 함께 적는다.**

### 단위계 — **선언하고, 환산값을 원본 옆에 놓는다** (2026-09-24)

**재료 API 의 응답 하나 안에 두 계가 섞여 있다**: `density` 는 화면 표시값이라 단위가
`density_unit`(`tonne/mm3`)에 따로 있고, `declared_properties[].points[].value_si` 는 SI 다.
**값마다 단위가 붙어 있어 숫자 자체가 틀린 것은 아니다** — 받는 쪽이 「전부 SI」 라고 가정할
때 틀린다. 우리 STEP 은 mm 이라 해석은 mm·tonne·s 로 푸는데, 그렇게 가정하면 **밀도는 맞고
탄성계수가 10⁶ 배 틀린다** — 결과가 안 나오는 것이 아니라 **그럴듯한 값이 나오고 틀린다.**

> **MatNexus 가 바로잡아 준 것** (2026-09-24). 내 첫 분석에 틀린 데가 셋 있었다:
> ① 「135건 전부 `tonne/mm3`」 는 **단위 글자**를 센 것이다 — 밀도 값이 실제로 있는 재료는
> 18개다. ② 「단위는 6종뿐」 은 재료 API 에만 맞다 — 물성 카드에는 `K` · `s` · `1/s` ·
> `Hz` · `Pa.s` 가 더 있어 **11종**이고, 6종으로 굳혔으면 점탄성 카드를 받는 날 조용히
> 지나갔을 것이다. ③ 「`mm·kg·s` 면 힘이 μN」 은 틀렸다 — **mN** 이고 응력은 kPa 다
> (요점인 「`mm/kg/s/N` 은 앞뒤가 안 맞는다」 는 맞다).
>
> 그리고 **`density_si` 칸이 생겼다**(대화 중에). 있으면 그것이 정본이라 거기서 출발한다.

| | |
| --- | --- |
| 고를 수 있는 계 | `mm_n_tonne`(기본 — CAD 가 mm) · `si`. **열쇠를 MatNexus 와 맞췄다** |
| 선언 | `conditions.units` → 내보낼 때 **닫힌 한 벌**로 펼쳐진다(force · stress · density …) |
| 환산 | 물성마다 `converted` 를 **`payload` 옆에** 싣는다. 원본은 안 건드린다 |
| 못 바꾼 것 | `converted.unconverted` 에 이름이 남는다 — 조용히 두면 새 단위인 줄 알고 푼다 |

**「어느 것이 영률인가」 는 여전히 안 본다.** 환산에 필요한 것은 단위 문자열뿐이고
(`2.06e11 Pa` → `206000 MPa`), 그 값이 무슨 물리량인지는 몰라도 된다 — 6장의 결정과 다른
축이다. 차원(M·L·T·Θ 지수)으로 풀므로 비열처럼 길이가 제곱으로 들어가는 것도 맞는다
(880 J/(kg·K) → 8.8e8 mJ/(tonne·K); 「응력이니까 10⁶」 같은 눈대중으로는 안 나온다).

**표에 없는 단위는 건드리지 않는다.** 짐작해서 바꾸면 틀린 값이 맞는 얼굴로 나간다.

**환산은 한 곳에서만 한다**(`core/units.py`). 물성 탐색기가 보여 주는 값도 서버가 같은
함수로 만들어 준다(`GET /materials?system=`) — 프런트에 표를 두면 두 벌이 어긋나고, 그때
**화면이 보여 준 값과 내보낸 값이 달라진다.**

### 그쪽과 어긋나면 **검사가 말한다**

MatNexus 는 단위계를 1급으로 들고 있다(`GET /api/fitting/unit-systems` — 계마다 기호표까지).
우리도 제 표를 든다: **런타임에 그쪽을 의존하지 않으려는 것**이다(MatNexus 가 꺼져 있어도,
올려 둔 사본으로 골라도 내보내기는 돼야 한다).

대신 `scripts/check_matnexus.py` 가 **맞춰 본다**(`core/units_check.py`) — 계 이름 · 기호 ·
우리가 못 읽는 단위. **표가 아니라 행동을 비교한다**(실제로 환산해 보고 그 답을 맞춘다) —
표만 보면 「값이 안 바뀌는 차원은 들어온 기호를 그대로 둔다」 같은 규칙을 놓친다. 실제로
그 검사가 **`Hz` 를 우리가 `1/s` 로 바꿔 내보내던 것**을 잡았다: 값은 같아도 그쪽이 쓴 말을
우리가 바꾼 것이고, 그러면 되돌아온 파일이 원본과 안 맞는다.

### 「확정 물성 카드」 — 더 나은 길이지만 아직 재료가 없다

MatNexus 는 다른 시스템과 주고받는 경로로 **확정 카드**를 권한다. 처음에 나는 「카드는 솔버별
덱이라 우리 중립 계약과 안 맞는다」 고 적었는데 **그건 불완전했다**: 형식 목록에
`{"key": "json", "label": "중립 JSON", "describe": "솔버 중립"}` 이 있다. 중립으로 받을 수 있다.

카드가 문헌 값보다 나은 점:

- **사람이 확인해 굳힌 값**이다(`status: published`). 문헌 스칼라가 아니라 맞춘 결과다 —
  실제로 본 카드의 탄성계수는 `youngs_modulus_source: "prony"` 였다.
- **단위계를 골라 받는다**(`?format=json&units=mm_n_tonne`). 우리가 환산할 필요가 없고,
  **모르는 단위는 변환하지 않고 거절한다** — 우리와 같은 태도다.
- 응답에 `units` 선언과 블록별 `declared`(항목마다 `si_unit`)가 함께 온다.

**그런데 펴낸 카드가 2장뿐이다**(전체 37장 중 draft 32 · deprecated 3, 2026-09-24). 지금
갈아타면 고를 수 있는 재료가 거의 없어진다. 그래서:

- **지금은** 문헌 물성(`/api/materials`, `density_si` 포함)을 스냅샷으로 뜨고 우리가 선언과
  함께 환산한다.
- **카드가 쌓이면** 「펴낸 카드가 있으면 그것, 없으면 문헌」 으로 바꾼다. 그때 고칠 자리는
  스냅샷을 뜨는 한 곳이다.

**우리 환산이 그쪽 카드와 숫자까지 같은 것은 확인했다** — 같은 카드를 SI 와 `mm_n_tonne` 로
각각 받아, SI 값을 우리가 환산한 것과 그쪽 값을 맞춰 본다(`check_matnexus.py` 의 「숫자」 줄,
상대오차 1e-9). 기호 이름만 맞추면 **배수가 틀려도 모른다.**

> 곁들여 고친 것: `Units` 의 예전 기본값이 `mm · kg · s · N` 이었다. **닫히지 않는 계**다
> (mm·kg·s 에서 힘은 mN, 응력은 kPa — MatNexus 가 내 첫 계산의 μN 을 바로잡아 줬다).
> 이제 고를 수 있는 것은 **계 이름뿐**이고 나머지는 계산한다 — 그런 조합을 적을 수 없게.

### 단위 — payload 는 건드리지 않는다

| 자리 | 무엇을 하나 |
| --- | --- |
| MatNexus → 이 플랫폼 | **아무것도 안 한다.** SI 값과 `si_unit` 이 붙은 채로 저장 |
| 이 플랫폼의 자체 계산 | 그 자리에서만 mm · MPa 계로 환산(위 2번 규칙 아래) |
| 이 플랫폼 → SimEngBay | payload 를 그대로 싣는다. `MaterialSpec`(GPa · kg/m³)을 채우는 것은 **받는 쪽** |

**중간에 정규화 층을 두지 않는다.** 두면 그 층이 언젠가 항목 이름을 잘못 알아듣고, 그 사실은
해석 결과가 이상할 때에야 드러난다.

### 권한은 **그쪽이 정한다** (2026-09-24 그쪽 개편 · 실측 v1.256.0)

MatNexus 의 권한이 **부서 트리 + 소속**으로 바뀌었다. 우리가 바꾼 것과 그 까닭:

| 전 | 후 | 왜 |
| --- | --- | --- |
| `scope=global` 을 코드가 박았다 | **지웠다** | 그 칸이 없어졌고, MatNexus 는 모르는 질의를 **조용히 무시**한다 — 그 뒤로 아무 필터도 아니었다(「전역 0건」 이던 화면이 개편 뒤 135건을 그대로 보여 줬다). 살아 있는 척하는 이름이 가장 나쁘다 |
| — | `MATNEXUS_WORKSPACE`(선택) | 부서가 여럿인 계정으로 붙었을 때 좁힌다. **권한이 아니라 좁히기다** — 토큰이 볼 수 있는 것보다 넓힐 수 없다 |
| 줄에 부서가 없었다 | `workspace`(=`owner_workspace_name`) | 두 부서에 같은 이름의 재료가 있을 수 있다. 안 보이면 고르는 사람이 구별 못 한다 |
| `ping()` 이 「연결됨」 만 말했다 | **누구로 붙었나**(`/api/auth/me`) · 보이는 건수 · 관리자 토큰 경고 | 붙기는 붙는데 계정이 달라 0건이거나, 반대로 관리자라 전부 보이는 일이 생긴다 — **적히지 않으면 아무도 모른다** |

**PAT 에는 여전히 범위가 없다**(토큰을 만들 때 정하는 것은 이름과 만료일뿐). 그러므로 경계는
**「이 토큰이 누구냐」 하나**이고, 우리가 질의로 권한을 흉내 낼 자리는 없다. 그래서 운영 결정이
하나 남는다: **읽기 전용 계정을 만들어 필요한 부서에만 넣는 것.** 지금 개발 연결은 시스템
관리자 토큰이라 부서 구분을 통째로 우회한다 — `scripts/check_matnexus.py` 가 그때마다 경고한다.

| # | 물음 | 답 (2026-09-23) |
| --- | --- | --- |
| 1 | 운영 서버에서 MatNexus 가 보이나 | **보인다.** 붙일 수 있다 |
| 5 | 어느 계정으로 붙나 | **미정 (2026-09-24)** — 지금은 시스템 관리자 토큰이다. 읽기 전용 계정 + 부서 배정이 필요하고, 그것은 MatNexus 쪽에서 만들 일이다. 코드는 이미 둘 다 받는다 |
| 2 | 탄성계수 키가 고정인가 | **묻지 않기로 했다** — 통째로 나르므로 우리가 알 필요가 없다 |
| 3 | 온도 표 표현 | `DeclaredPropertyOut.points[]`(온도 오름차순) + `si_unit` + `scale`. **그대로 싣는다** |

## 7. 화면 — CAD 모드와 시뮬레이션 모드

### 어디에 붙이나

지금 화면은 이렇게 갈려 있다:

```
/works/{id}   내 작업 하나 — 탭 「도면」(RecipeEditor 로 들어가 그린다)
/doe          실험계획 공간 — 대상(작업)을 고르고 변수에 범위를 준다
```

작업 화면 머리말이 정해 둔 선이 있다 — 「**여러 벌을 만드는 일은 여기서 하지 않는다.**
도면을 저장할 때까지 하는 일은 그리기와 변수 심기뿐이다.」 조건은 그 선의 **어느 쪽인가**?

**조건은 형상의 성질이다 — 작업에 붙인다.** 「이 지그는 바닥으로 시험대에 앉는다」 는 이 형상을
어떻게 훑든 변하지 않는다. 그래서 작업 버전에 붙이고, **DOE 는 레시피처럼 스냅샷을 뜬다**
(이번 훑기에서만 다르게 하려면 스터디에서 덮어쓴다).

### 모드 셋

| 모드 | 어디 | 무엇을 하나 | 왜 갈랐나 |
| --- | --- | --- | --- |
| **CAD** | `RecipeEditor`(전체 화면) | 형상을 만든다. 리본에 **「영역」 그룹**을 더해 `divide_face` 와 영역 이름표를 둔다 | 면을 나누는 것은 **형상을 바꾸는 일**이라 레시피 노드다. 편집기 밖에 두면 되돌리기 · 버전이 갈라진다 |
| **시뮬레이션** | `/works/{id}` 의 **둘째 탭 「해석 조건」** | 이미 있는 형상 위에 조건을 붙인다 | 조건은 형상을 안 바꾼다. 그리는 일과 섞으면 리본이 두 배가 되고, 「저장하면 형상이 바뀌나」 를 매번 묻게 된다 |
| **훑기** | `/doe` | 대상 + 변수 범위 + **어느 조건 벌을 쓰나** | 이미 있는 자리. 「이 작업의 v3 조건을 쓴다」 한 줄과 미리보기만 더한다 |

DOE 폼의 변수 목록은 지금도 레시피의 `params` 에서 온다. **조건 변수도 같은 자리에 있으므로
그대로 나온다**(3장) — 다만 줄 옆에 **어디에 쓰이는지**를 적는다: 「두께 — 형상 · 하중」,
「압력 — 하중」. 형상에 안 쓰이는 변수를 보고 「이게 왜 여기 있지」 를 묻지 않게.

작업 화면의 탭이 곧 모드 전환이다(`도면` ↔ `해석 조건`). 탭이 지금 하나뿐이라 **둘째 탭이
생기는 것이 곧 시뮬레이션 모드**다 — 새 화면도, 새 메뉴도 필요 없다.

### 「해석 조건」 탭의 생김새

세로 3분할. 가운데 3D 가 주인공이고 양옆이 그것을 설명한다.

```
┌─ 조건 ──────────┬─ 3D (PickViewer) ─────────────┬─ 속성 ─────────────┐
│ ▸ 이름표(영역) 4 │                               │ 고정: 바닥면        │
│    바닥면        │     [면 · 엣지 · 점 고르기]    │ 대상: 이름표 「바닥면」│
│    볼트구멍 ×4   │                               │ 셀렉터: role=bottom │
│    하중영역      │     고른 것은 노랗게,          │   ↳ 지금 1면에 맞음  │
│ ▸ 물성 1        │     이름표는 제 색으로          │ 종류: 완전 고정 ▾    │
│ ▸ 접촉 1        │                               │                     │
│ ▸ 구속 2        │                               │ [지우기]            │
│ ▸ 하중 1        │                               │                     │
│ ▸ 초기조건 0     │                               │                     │
│ ▸ 해석 설정      │                               │                     │
│ ▸ 메시 힌트 2    │                               │                     │
│ [+ 이름표] [+조건]│                               │                     │
└─────────────────┴───────────────────────────────┴─────────────────────┘
```

**규칙 셋:**

1. **이름표를 먼저, 조건은 그 위에.** 조건은 면을 직접 가리키지 않고 **이름표만** 가리킨다
   (3장). 그래야 같은 면에 하중과 메시 힌트를 따로 걸어도 한 군데만 고치면 된다.
2. **고른 것을 말로 되돌려 준다.** 3D 에서 바닥면을 클릭하면 좌표가 아니라 **셀렉터 후보**를
   보여 준다 — 「아래쪽 면(role=bottom)」 · 「이 점에서 가장 가까운 면」 · 「반지름 4.25 원통면
   (4개)」. 사람이 고르고 고칠 수 있어야 한다. **왜 좌표로 저장하지 않는지**는 1장 ①.
3. **지금 몇 개에 맞는지 늘 보여 준다.** 「role=bottom → 1면」, 「radius=4.25 → 4면」. 설계점을
   바꿔 보면 그 수가 변하는지도 여기서 확인한다(`미리보기: 두께 12 에서도 4면`).

### 조건마다 칸이 다르다 — 폼은 사양표에서 나온다

종류가 열 몇 가지이고 칸이 제각각이다(고정 지지에는 값이 없고, 압력에는 크기와 방향이,
볼트 예압에는 N 또는 mm 가 있다). 화면에 `if` 를 늘어놓으면 종류를 더할 때마다 화면을 고쳐야
한다. **CAD 리본이 이미 쓰는 방식을 그대로 쓴다** — `recipeSpec.ts` 의 `OP_SPECS` 가 노드마다
칸을 적어 두고 `NodeForm` 이 그걸로 폼을 그린다. 조건도 같게:

```ts
CONDITION_SPECS = {
  fixed_support:   { group: '구속', fields: [] },
  displacement:    { group: '구속', fields: [
                       { name: 'x', kind: 'number|free' }, … ] },
  pressure:        { group: '하중', fields: [
                       { name: 'magnitude_MPa', kind: 'number', min: 0 },
                       { name: 'direction', kind: 'enum', of: ['normal', 'vector'] } ] },
  bolt_pretension: { group: '하중', fields: [{ name: 'preload_N', kind: 'number' }] },
  frictional:      { group: '접촉', fields: [
                       { name: 'friction', kind: 'number', min: 0, max: 1 }, … ] },
  …
}
```

**정본은 서버다** — 백엔드 스키마(Pydantic)가 같은 사양을 들고 `GET /conditions/schema` 로 준다.
CAD 레시피가 `recipe_schema` 로 하는 것과 같다. 그래야 AI(MCP)와 화면이 **같은 표**를 본다.

### 물성은 탐색기를 부른다

「물성」 줄에서 `[MatNexus 에서 고르기]` → 6장의 탐색기(대화상자) → 고른 것이 payload 째로
붙는다. 어느 바디에 붙일지는 `bodies` 목록에서 고른다(5장).

## 9. 아직 안 정한 것

- ~~**`/filter` · `/tradeoff` · `DoePoint.metrics` 를 걷어낼까.**~~ **걷어냈다**(0013).
  결과를 받지 않기로 했으므로(0장) 이 셋은 채워질 일이 없었다 — 빈 답을 내는 코드였다.
- **`divide_face` 의 자르는 도형 범위** — 원 · 사각만인가, 기존 `sketch` 노드를 그대로 쓰나.
  스케치를 쓰면 공짜로 강력해지지만 투영 규칙을 정해야 한다.
- **영역 이름 사전** — 받는 쪽마다 기대하는 이름이 다를 수 있다. 우리는 **사람이 지은 이름**을
  그대로 싣고(중립), 매핑은 받는 쪽에 둔다. 다만 기본 영역 둘(`fixed_base` · `bolt_holes`)은
  [SimEngBay/docs/용어.md](../../SimEngBay/docs/용어.md) 와 맞춰 둔다.
- **MatNexus 렌더러를 언제 부르나** — 온도 의존 · 소성이 필요해지는 시점. 그 전까지는 payload
  의 스칼라로 간다(6장 표 4번).
