# 동역학 조건 설계 — 기구와 유연체를 같은 폴더로 넘긴다

> 작성 2026-10-30 · **초안**(받는 쪽과 계약을 맞추기 전). 바탕은 [해석-조건-설계.md](해석-조건-설계.md)
> 다 — 그 문서의 경계 · 선택 그룹 · 좌표계 · 단위 · `"=식"` 규칙을 그대로 쓰고, 이 문서는 **동역학
> (다물체 · 기구) 해석에 더할 것**만 적는다. 해석기 후보는 Ansys Motion · Exudyn, 그다음 Chrono ·
> MuJoCo 다. 계획은 9장, 받는 쪽과 정할 것은 10장, Motion API 를 공개 문서로 본 것은 12장, 이 PC 의
> Mechanical 에 든 Motion 확장에서 본 것은 13장, Exudyn 으로 계약을 시험한 것은 14장.

## 0. 경계 — 그대로다

```
오케스트레이터
  ├─ CompCore MCP     doe_run → 폴더 (형상 · 조건 · 설계점)              (있다)
  ├─ SimEngBay MCP    정적 · 모달 · 조화 · 열, 그리고 축약 유연체(5장)     (있다 · 유연체는 새로)
  └─ 동역학 해석 MCP   Motion · Exudyn … — 폴더 + 유연체 파일 → 과도 해석    (새로)
```

**이 플랫폼은 메시도 솔브도 하지 않고, 결과도 받지 않는다**(해석-조건-설계 0장 · ADR 0010) —
동역학도 같다. 하는 일은 지금처럼 **설계점마다 형상과 솔버를 모르는 중립 조건**을 내보내는 데까지다.
「MCP 로 동역학 · 선형 · 모달을 모두 돌린다」 는 그림은 오케스트레이터가 위의 MCP 들을 차례로 부르는
꼴이다 — 데이터는 폴더로, 명령과 상태는 MCP 로(오케스트레이션-연계-설계 0장).

**동역학 전용 전처리 툴을 따로 만들지 않는다.** 까닭은 셋이다.

- 동역학이 CAD 에서 가져갈 것이 **여기 이미 있다**(1장) — 형상 레시피와 DOE, 설계점마다 다시 푸는
  선택 그룹, 면을 따라가는 좌표계, MatNexus 물성.
- 따로 두면 가장 어려운 부분(형상 · 선택 그룹 · DOE · 물성 · 폴더 계약 · 픽스처 판정)이 **두 벌**이
  된다. 두 벌이면 한쪽만 고쳐진다.
- **같은 설계점을 구조와 동역학이 함께 쓴다.** 동역학의 관절 반력을 같은 형상의 정적 해석 하중으로
  넘기는 길이 폴더 하나로 이어진다. 유연체의 접속점이 조인트 자리와 맞는 것(5장)도 그래서 된다.

이 문서가 다루지 않는 것: CAD 에서 나오지 않는 모델(차량 · 타이어 · 노면처럼 해석기 안에서 짠 것),
형상을 훑지 않고 구동만 바꾸는 일. 그런 일이 주라면 CompCore 가 줄 것이 적다.

## 1. 이미 있는 것

| 동역학이 쓰는 것 | 있는 자리 | 비고 |
| --- | --- | --- |
| 형상 · 조립 · **처음 자세** | 설계점 STEP, 조립의 구성품 = 바디 | t = 0 자세는 레시피의 자리 그대로 — 회전 노드에 `"=식"` 을 쓰면 처음 각도도 DOE 로 훑는다 |
| 바디 짝짓기 | 점 파일 `bodies[]`(`name` · `step_product` · 부피 · 무게중심 · 경계상자) | 해석-조건-설계 5장 |
| 조인트 자리 · 축 | `coordinate_systems` — `on` 이 원통면 그룹이면 원점 = 면 중심, **Z = 원통 축**([frames.py](../backend/app/core/frames.py) `condition_frames`) | 설계점마다 그 면을 따라간다 |
| 물성 | `materials[].snapshot`(밀도 · E · ν, 단위 환산까지) | 6장 「물성」 |
| 강체 | `body_settings[].behavior: rigid` | 3장 |
| 중력 | `loads[]` 의 `standard_earth_gravity` | 그대로 쓴다 |
| 처음 속도 | `initial[]` 의 `velocity`(바디 그룹) | 그대로 쓴다 |
| 시간 | `analysis` 의 `end_time` · `output_count`(명시적 · 열 과도) | 2장에서 `multibody` 로 넓힌다 |
| 원격점과 그 거미줄 | 원격 변위의 `location: cs_origin` · `behavior: rigid/deformable` | 유연체 접속점(5장)이 이 모양이다 |
| 판의 중간면 | `representation: shell` → `pNNNN_mid.step` | 셸 유연체가 솔리드보다 훨씬 가볍다 |
| 같은 형상 | 점이 가리키는 `shapes/<지문>.step` | 유연체를 다시 쓰는 열쇠의 한 조각(5장) |
| 초기 자세 간섭 | `recipe_interference` | 처음 자세에서 바디가 겹치면 솔버가 첫 걸음에 튄다 |

## 2. 해석 종류 — `multibody`

```jsonc
"analysis": {
  "type": "multibody",
  "end_time": 2.0,          // s — 있는 칸(명시적 · 열 과도)을 넓힌다. 필수
  "output_count": 200,      // 있는 칸
  "max_time_step": 0.001    // s — 새 칸. 적분 간격의 상한, 비우면 솔버가 정한다
}
```

- **`explicit` 과 다르다.** 명시적은 FE 메시의 충돌 · 낙하이고, `multibody` 는 강체 · 유연체를
  조인트로 이은 기구다.
- 내보낼 때 이 종류의 칸만 기본값을 채워 싣는다(`_filled_analysis`) — 지금 규칙 그대로.
- 다음 후보: 시작 전 정적 평형(`initial_equilibrium`), 적분기 고르기. 받는 쪽이 쓰는지 보고 넣는다.
- **한 스터디에 해석은 하나다.** 같은 설계점을 모달과 동역학으로 함께 풀려면 처음에는 같은 인자 ·
  시드로 스터디를 둘 만든다. 해석 여럿을 한 스터디에 싣는 것은 필요해질 때 따로 정한다.

## 3. 파트 — 강체 · 유연체 · 질량

### 거동

- **`multibody` 에서는 적지 않은 파트를 강체로 읽는다.** 지금 기본값은 「변형체」 인데, 그대로면
  기구의 모든 파트가 유연체(메시 · 모드)가 된다. 강체가 기구 해석의 보통이고 유연체는 고른 것이다.
- 기본값이 해석 종류마다 달라지므로 **내보낼 때 모든 파트의 `behavior` 를 적는다** — 받는 쪽이
  「안 적힌 것은 무엇인가」 를 짐작하지 않게.
- `deformable` 은 유연체다 — 그 방식은 `flex` 칸(5장). 「해석 제외」(`suppressed`)는 그대로다.
- 강체 쉘은 지금도 막는다 — 그래서 **강체는 늘 솔리드**다.

### 질량 · 관성 — 우리가 낸다

강체 동역학에서는 **질량 · 무게중심 · 관성이 곧 모델**이다. 해석기마다 형상에서 따로 재게 두면
Motion · Exudyn · Chrono 가 서로 다른 질량으로 풀고, 두 솔버 대조가 「질량이 달라서」 로 끝난다.
그래서 CompCore 가 재서 싣는다 — 붙여 준 Motion 0단계의 「질량 자동 계산 확인」 이 필요 없어진다.

```jsonc
"bodies": [
  { "name": "크랭크", "step_product": "crank", "kind": "solid", "volume": 18840.0, …,
    "mass": 5.09e-5,                          // t (mm_n_tonne) — si 면 kg
    "center_of_mass": [12.0, 0.0, 4.0],       // 무게중심, 전역
    "inertia": [1.2e-3, 4.8e-3, 5.6e-3, 0.0, 0.0, 0.0] }   // t·mm² — 무게중심 기준 ·
]                                                          //   전역 축, [Ixx, Iyy, Izz, Ixy, Iyz, Ixz]
```

- **밀도는 조건의 물성에서** 온다(`materials[].converted.density` — 내보내기 계의 값). 셈은
  [digest.py](../backend/app/core/recipe/digest.py) `body_mass`(밀도 · 단위계 → 질량 · 무게중심 · 관성,
  그 계의 단위)와 [conditions.py](../backend/app/core/conditions.py) `body_density`(파트 → 밀도)가 한다
  (2026-11-01). `mass_properties` 는 재료 이름 · g 로 내는 AI 치수표로 남는다. 점 파일에 싣는 것은
  어디에 실을지(10장 5)를 정하고 나서다.
- 관성은 **무게중심 기준**이다(원점 기준이면 형상을 옮기기만 해도 값이 바뀐다 — digest 와 같은 까닭).
  곱관성의 부호(Ixy = −∫xy dm 인가 +∫xy dm 인가)는 솔버마다 다르다 — 점 파일에 약속을 적는다(10장).
  지금 `mass_properties` 가 내는 행렬은 **관성 텐서**다 — 비대각이 −∫xy dm(L 자 손셈으로 확인, 14장).
  Exudyn 은 그대로 받는다.
- **밀도가 없는 강체 파트가 있으면 막는다.** 질량이 없는 강체는 기본값으로 풀려 그럴듯한 답이 난다 —
  물성 없는 바디를 막는 것과 같은 까닭이다.
- 유연체는 솔버가 메시에서 질량을 잰다. 그래도 같은 값을 싣는다 — 받는 쪽이 메시의 질량과 견줘 메시가
  형상을 다 덮었는지 본다.
- **처음에는 `multibody` 일 때만 싣는다.** 구조 픽스처 폴더가 바뀌지 않게. 모든 해석에 실을지는 받는
  쪽과 정한다(10장).

## 4. 조인트 · 구동 · 힘 요소 · 출력

### 조인트

```jsonc
"coordinate_systems": [
  { "name": "축A", "on": "크랭크 축구멍" },     // 원통면 그룹 — 원점 = 축 위, Z = 축
  { "name": "핀B", "on": "크랭크 핀" }
],
"joints": [
  { "name": "크랭크 축", "type": "revolute", "base": "ground", "action": "크랭크", "cs": "축A" },
  { "name": "크랭크-링크", "type": "revolute", "base": "크랭크", "action": "링크", "cs": "핀B" },
  { "name": "슬라이더", "type": "translational", "base": "ground", "action": "피스톤", "cs": "미끄럼" }
]
```

| `type` | 뜻 | `cs` 의 Z |
| --- | --- | --- |
| `fixed` | 붙인다 | 원점만 쓴다 |
| `revolute` | 축 하나로 돈다 | 회전축 |
| `translational` | 축 하나로 미끄러진다 | 미끄럼 방향 |
| `cylindrical` | 돌고 미끄러진다 | 축 |
| `spherical` | 한 점에서 돈다 | 원점만 쓴다 |

- 다음 후보: `universal` · `planar` · 기어 · 캠. 1차는 위 다섯이다.
- `base` · `action` 은 `bodies[].name` 이거나 **`ground`**(바닥)다. 둘이 같으면 막는다.
- **`cs` 의 Z 가 축이다** — 바디 볼트 예압의 단면과 같은 약속이다(2026-10-28). 축을 선택 그룹이
  아니라 좌표계로 가리키는 까닭: 같은 자리를 조인트 · 유연체 접속점 · 힘 요소 · 출력이 함께
  가리켜야 하고(5장), 좌표계는 이름 하나로 그 자리를 설계점마다 다시 푼다.
- 좌표계의 원점은 **축 위에 있어야** 한다. 원통면이 반쪽 둘로 갈려 있으면 면 중심이 축 밖이라
  (경계상자 중심이 r/2 벗어난다 — 실측), 회전면 지문의 `axis_at`(축 위의 점)에 선다(2026-11-01, 11장).
- 구멍에 붙인 좌표계의 원점은 **그 바디 구멍의 깊이 가운데**다. `revolute` · `cylindrical` 은 축 위
  어디든 같지만, `spherical` 은 그 점에서 두 바디가 만나야 한다 — 두 바디의 구멍이 층을 달리하면(슬라이더
  크랭크의 링크와 피스톤) 어느 쪽 구멍을 골랐느냐로 점이 달라진다. 구면 조인트는 구면 · 점 그룹에 붙인다.
- **평면 기구는 3D 조인트로 지으면 과구속이다** — 슬라이더크랭크(회전 셋 + 미끄럼)는 중복 구속이 셋이다.
  사람에게 조인트를 바꾸라고 하지 않는다 — 해석 쪽이 다룬다(Exudyn 은 풀이기 설정으로 풀린다, 14장).
  과구속 방향의 반력(면 밖 힘 · 모멘트)은 하나로 정해지지 않으므로 판정은 평면 안 성분으로 한다.

### 구동

```jsonc
"drivers": [
  { "name": "모터", "joint": "크랭크 축", "kind": "angular_velocity",
    "profile": { "type": "ramp", "t": [0, 0.2], "value": [0, "=회전수 * 2 * pi / 60"] },
    "unit": "rad/s" }
]
```

- `kind` 는 조인트가 허락하는 것만 — 회전 조인트는 `angle` · `angular_velocity` ·
  `angular_acceleration`, 미끄럼 조인트는 `displacement` · `velocity` · `acceleration`. 원통 조인트는
  어느 쪽인지 적는다.
- `profile`: `constant`(값 하나) · `ramp`(두 점 사이 직선) · `sine`(진폭 · 주파수 · 위상 · 기준) ·
  `table`(`[[t, 값], …]`). 숫자 칸은 모두 `"=식"` 이 된다 — 모터 회전수도 DOE 인자다.
- **단위를 값에 붙인다**(`unit`). 지금 칸들은 이미 섞여 있다 — 원격 변위의 회전은 **도**, 회전 속도
  하중은 **rad/s** 다. 볼트 예압이 `unit` 으로 힘 · 길이를 고르듯 구동도 한 칸에 단위를 적는다. 비우면
  단위계에서 채운다(각도는 도).
- 모터 토크 한계는 해석기가 받는지 보고 넣는다(10장).
- **정지에서 정속 구동을 바로 걸면 첫 걸음에서 토크가 튄다.** Exudyn 슬라이더크랭크에서 정상 최대의
  약 1000 배(14장)였다 — 「최대 모터 토크」 를 읽는 사람이 그 값을 받는다. 처음 속도를 구동에 맞춰 주거나
  (`initial[].velocity` — 기구 전체를 맞추는 것은 해석 쪽 몫이다) `ramp` 로 올린다. 픽스처는 `ramp` 로 쓴다.

### 힘 요소

```jsonc
"force_elements": [
  { "name": "복귀 스프링", "type": "spring_damper", "base": "ground", "action": "레버",
    "base_at": "스프링 아래", "action_at": "스프링 위",      // 두 좌표계의 원점 사이
    "stiffness": 5.0, "damping": 0.01, "free_length": null }, // N/mm · N·s/mm · 비우면 처음 길이
  { "name": "고무 부싱", "type": "bushing", "base": "프레임", "action": "암", "cs": "부싱A",
    "stiffness": [800, 800, 200], "rotational_stiffness": [5e4, 5e4, 1e4],   // N/mm · N·mm/rad
    "damping": [0.5, 0.5, 0.2], "rotational_damping": [10, 10, 2] },
  { "name": "외력", "type": "force", "action": "피스톤", "cs": "피스톤 머리",
    "direction": [0, 0, -1], "profile": { "type": "constant", "value": 200 }, "unit": "N" }
]
```

- 종류: `spring_damper`(두 점 사이) · `bushing`(한 자리의 6 성분) · `force` · `torque`(바디에 거는
  외력 — 그 좌표계의 원점에, `profile` 로 시간에 따라).
- 회전 강성은 **rad** 기준이다(N·mm/rad) — 각도 입력이 도인 것과 다르다. 그래서 단위를 값에 붙인다.
- 단위계에 차원을 더한다: 질량 · 관성 · 감쇠(N·s/mm) · 회전 강성 · 회전 감쇠(`core/units.py`).

### 구조용 칸은 `multibody` 에서 받지 않는다

| 구조 | `multibody` 에서 | 까닭 |
| --- | --- | --- |
| `constraints`(면 고정 · 변위) | **받지 않는다** — `ground` 와의 `fixed` 조인트로 | 강체 기구에는 「면」 을 묶을 메시가 없다 |
| `loads` 의 면 하중(압력 · 힘 · 모멘트 · 베어링 · 볼트) | **받지 않는다** — `force_elements` 의 `force` · `torque` 로 | 지금 규칙이 강체에 하중을 막는다(`_check_rigid`) — 기구에서는 강체 외력이 보통이라 다른 자리에 둔다 |
| `standard_earth_gravity` · `initial[].velocity` | 그대로 | |
| `contacts` | **1차에서 뺀다** | 동역학 접촉(강성 · 감쇠 · 반발)은 지금 칸(Ansys Mechanical 의 말)과 뜻이 다르다 — 섞지 않고 따로 설계한다 |
| `mesh_hints` | 유연체에만 | 강체에는 메시가 없다 |

받지 않는 칸이 차 있으면 **막는다** — 조용히 버리면 사람이 건 조건이 빠진 채 그럴듯한 답이 난다.

### 출력

```jsonc
"outputs": [
  { "type": "joint_reaction", "joint": "크랭크-링크" },      // 힘 · 모멘트, 조인트 cs 성분
  { "type": "driver_effort", "driver": "모터" },             // 모터 토크 · 힘
  { "type": "body_motion", "body": "피스톤", "at": "피스톤 머리" },  // 그 좌표계 원점의 변위 · 속도 · 가속도
  { "type": "flex_stress", "body": "링크" }                  // 유연체 응력(5장)
]
```

시간 이력은 그 점에서 어디를 읽어야 하는지 정하지 않으면 남지 않는다 — 구조 해석의 「측정점」 과 같은
자리다. 결과는 해석 쪽 화면에서 본다(ADR 0010).

## 5. 유연체 — 접속점이 핵심이다

### 두 갈래

| | 축약 유연체(모달 · CMS) | 전체 FE 유연체 |
| --- | --- | --- |
| 언제 | 작은 변형 — 대부분의 기구 | 큰 변형 · 비선형 재료 · 접촉 |
| 누가 메시 · 모드를 만드나 | **구조 솔버** — Craig-Bampton 같은 축약으로 모드를 뽑아 파일로 | 동역학 솔버가 직접 |
| 동역학 쪽이 받는 것 | 유연체 파일(모드 · 접속점) | 형상 + 메시 힌트 |
| 비용 | 모드 수만큼 — 빠르다 | 요소 수만큼 — 느리다 |

Exudyn 은 FEM 모듈에 Craig-Bampton 모드 계산이 있다(받는 쪽이 확인). Motion 은 공개 API 문서로 보면
**두 길**이 있다(12장): CAD 솔리드 바디에 바로 거는 EasyFlex(면을 골라 강체 요소 쌍을 붙인다)와, Nastran
`bdf` · `dat` 메시를 들이는 노드 바디(따로 받는 모달 파일로 모달 바디가 된다). 모달 파일은 `.dfmf` 이고,
Ansys 의 DPF 가 MAPDL 축약(CMS) 결과에서 그것을 쓴다(13장).

### 칸

```jsonc
"body_settings": [
  { "name": "링크", "behavior": "deformable",
    "flex": { "method": "modal", "modes": 12, "max_frequency": 2000, "damping_ratio": 0.02 },
    "mesh": { "element_size": 2.0, "order": "quadratic" } },
  { "name": "크랭크", "behavior": "rigid" }
],
"joints": [
  { "name": "크랭크-링크", "type": "revolute", "base": "크랭크", "action": "링크", "cs": "핀B",
    "interface": { "action": "링크 구멍B", "behavior": "rigid" } }
]
```

- `flex.method`: `modal`(축약) · `full`(전체 FE). `modes` 또는 `max_frequency` 중 하나는 있어야 한다
  (모달 해석의 `modes` · `frequency_range` 와 같은 뜻). `damping_ratio` 는 모드 감쇠다.
- 판 파트는 `representation: shell` 로 — 중간면 STEP 이 함께 나가고(지금 그대로), 셸 유연체가 된다.
- **접속점은 조인트에서 나온다.** 유연체에 걸린 조인트가 곧 그 유연체의 접속점(축약의 경계 자유도)이다.
  사람이 정할 것은 **거미줄이 붙을 면**(`interface` 의 그 쪽 선택 그룹)과 그 거동(`rigid` = RBE2 ·
  `deformable` = RBE3)뿐이고, 원점은 조인트 `cs` 의 원점이다 — 원격 변위의 `location: cs_origin` 과
  같은 모양이다. 힘 요소 · 출력이 유연체의 자리를 가리켜도 같은 식으로 접속점이 하나 는다.
- 유연체 쪽에 `interface` 가 없으면 막는다. 강체 쪽에는 적지 않는다(적으면 막는다).

### 왜 접속점이 핵심인가

두께를 훑으면 구멍 자리가 움직인다. 유연체의 접속점과 조인트의 자리를 **따로** 적으면 설계점마다
어긋난다 — 유연체는 옛 자리에서 붙고 조인트는 새 자리에서 돈다. 이 어긋남은 해석이 멈추지 않고
「조금 다른 기구」 로 끝까지 돈다.

여기서는 **좌표계 하나**(「핀B」 — 원통면에 붙음)를 조인트와 유연체 접속점이 함께 가리킨다. 그 좌표계는
설계점마다 그 면을 다시 풀어 따라가므로 둘이 늘 같은 자리다. 별도 툴이면 이 자리를 두 번 정의하게 되고,
그것이 가장 잘 깨지는 자리다.

### 누가 만드나 — SimEngBay 를 권한다

축약 유연체는 **구조 해석의 산출물**이다 — 메시 · 물성 · 모달이 필요하고, 그것은 SimEngBay 에 이미
있다(Ansys · CalculiX 두 솔버 대조까지). 그래서:

```
CompCore 폴더 ──▶ SimEngBay: 설계점마다 유연체 파일 + 자체 확인(모드 수 · 접속점 수 · 메시 질량)
            └──▶ 동역학 MCP: 강체(점 파일) + 유연체 파일 + 조인트 → 과도 해석
                     └▶ (선택) 관절 반력 이력 → SimEngBay 에서 응력 · 피로
```

동역학 MCP 가 직접 만들 수도 있다. **Motion 의 EasyFlex 는 SimEngBay 없이 된다** — STEP 의 솔리드 바디에
걸고 접속은 「면 + 점」 으로 정하는데(12장), 그것이 곧 우리 선택 그룹의 면 지문과 조인트 `cs` 의 원점이다.
노드 바디로 가면 메시를 만드는 쪽이 Nastran `bdf` 와 접속점마다 노드 세트(RBE2 · 주절점 자리)를 써야 한다.
모달 바디는 **SimEngBay 가 Motion 없이 만들 수 있다** — Ansys(MAPDL) 로 CMS 축약을 풀고 DPF 연산자
`compute_invariant_terms_motion` → `write_motion_dfmf_file` 로 `.dfmf` 를 쓴다(13장). 어느 쪽이든 CompCore
쪽 칸은 같다 — 10장.

### 같은 유연체인가 — 열쇠

유연체는 비싸다. 같은 것을 두 번 만들지 않으려면 「같은가」 를 알아야 하는데, **형상 지문만으로는
모자란다** — 물성 · 메시 · 접속점 · 모드 칸 중 하나만 달라도 다른 유연체다. 그것을 다 아는 것은
조건을 쓴 이쪽이라, 점 파일에 열쇠를 함께 싣는다:

```jsonc
"flex_bodies": [
  { "body": "링크", "key": "sha256:…",          // 형상 지문 + 물성 스냅샷 + 메시 + 접속점 + flex 칸
    "step_file": "shapes/c830bdfb634f.step",
    "interfaces": [ { "joint": "크랭크-링크", "origin": [60, 0, 5], "faces": [ … ] } ],
    "flex": { … }, "mesh": { … } }
]
```

같은 `key` 면 만드는 쪽이 다시 쓴다. 구동만 훑는 DOE 라면 모든 점이 같은 유연체 하나를 쓴다.

### 미리 만든 유연체 파일

설계를 훑지 않는 부품(프레임 · 하우징)은 이미 만든 유연체 파일이 있을 수 있다. 조건에서 그 파일을
참조로 가리키는 칸(`flex.source: "file"`)을 둘 수 있지만, 그 파일의 접속점이 우리 좌표계와 맞는지는
우리가 확인할 수 없다 — 필요한지부터 정한다(10장).

## 6. 막는 것

조건을 저장할 때 · DOE 를 만들 때 막는다(지금 `parse` 규칙에 더한다). 문장은 지금처럼 **어디가 ·
무엇이 · 어떻게 고치나**로.

- 조인트 · 힘 요소의 `base` · `action` 이 없는 파트이거나 둘이 같다.
- 조인트 · 힘 요소 · 출력의 `cs` 가 없는 좌표계다. 축이 필요한 조인트(`revolute` · `translational` ·
  `cylindrical`)에 좌표계가 없다.
- 구동의 `joint` 가 없거나, `kind` 가 그 조인트가 허락하지 않는 것이다.
- 밀도가 없는 강체 파트가 있다. 유연체 파트에 E · ν · 밀도 중 하나가 없다(`missing_structural`).
- 유연체 쪽 조인트에 `interface` 가 없다 · 강체 쪽에 있다 · 그 면이 그 파트의 면이 아니다(`_bodies_of`).
- `flex.method: modal` 인 파트의 재료가 비선형이다 — Motion 의 모달 바디가 받지 않는다(13장).
- `multibody` 인데 구조용 칸(4장 표)이 차 있다.
- 바닥(`ground`)과 이어지지 않은 파트는 **막지 않고 경고**만 — 자유롭게 나는 바디도 기구다. 자유도
  세기 · 과구속은 솔버마다 다르게 다루므로 경고로 둔다.
- 속도 · 각속도 구동이 0 이 아닌 값에서 시작하는데 그 바디의 처음 속도가 없으면 **경고** — 출발 충격(4장).

## 7. 점 파일에 더할 것

| 자리 | 무엇 | 언제 |
| --- | --- | --- |
| `bodies[]` | `mass` · `center_of_mass` · `inertia` | `multibody` |
| `conditions` | `joints` · `drivers` · `force_elements` · `outputs` — 식이 풀린 것 | `multibody` |
| `coordinate_systems[]` | 조인트 · 힘 요소 · 출력이 가리키는 좌표계(원점 · 축) | 있다 |
| `flex_bodies[]` | 유연체마다 열쇠 · 접속점(원점 + 면) · flex · 메시 | 유연체가 있을 때 |
| `warnings` | 바닥과 이어지지 않은 파트, 처음 자세에서 겹치는 바디 | 있을 때 |

`schema_version` 은 1 그대로다 — 모두 기본값이 빈 목록 · 빈 칸인 추가라 지금 폴더와 조건이 그대로
읽힌다. 받는 쪽은 `analysis.type` 이 `multibody` 가 아니면 새 칸을 볼 일이 없다.

## 8. 픽스처 — 답을 아는 기구

볼트 예압 폴더처럼 **손셈 판정을 README 에 먼저 적고**, 해석 쪽이 두 솔버(Exudyn · Motion)로 풀어
견준다(`fixtures/simengbay/README.md` 의 방식).

| 폴더 | 무엇 | 판정 |
| --- | --- | --- |
| `동역학_진자` | 강체 막대 하나 · 바닥과 회전 조인트 · 중력 · 작은 진폭 | 주기 T = 2π√(I_O / (m g d)), I_O = I_G + m d² — **점 파일의 질량 · 관성으로** 셈한다. 1 % 안 |
| `동역학_슬라이더크랭크` | 크랭크 · 링크 · 피스톤 강체, `ramp` 로 올린 정속 구동 | 피스톤 자리 x(θ) = r cos θ + √(l² − r² sin² θ), θ 는 구동 profile 을 적분한 각. 0.1 % 안. 모터 토크는 **다 오르고 0.3 s 뒤부터** 한 바퀴 주기로 되풀이(1 % 안), 그리고 **τ·ω = d(운동에너지)/dt**(1 % 안 — 질량 · 관성을 제대로 썼는지 본다) |
| `동역학_유연링크` | 외팔 유연 링크 + 끝질량, 바닥 정현 가진 | 1차 고유진동수는 `beam_frequency` 손셈 · SimEngBay 모달과 ±10 %. 그 주파수 가까이에서 끝단 응답이 커진다 |

두 솔버는 서로 5 % 안이 목표다(볼트 폴더와 같은 문턱). 판정이 틀렸으면 볼트 판본딩 때처럼 **실측에
맞춰 판정을 고친다** — 손셈이 무엇을 놓쳤는지 함께 적는다.

## 9. 계획

| 단계 | 무엇 | 끝의 기준 | 누가 | Motion |
| --- | --- | --- | --- | --- |
| 0 | 계약 맞추기 — 10장의 3 ~ 9 를 CompCore 가 근거(12 · 13 · 14장)로 정한다. 1 · 2 는 해석 쪽이 정해질 때까지 열어 둔다 | 3 ~ 9 를 ADR 로 남긴다 | CompCore | 아니오 |
| 1 | `multibody` 종류 · 거동 기본값 · 질량 · 관성 | 상자 · 원통 손셈과 질량 · 관성이 맞는 시험, 구조 픽스처가 그대로 | CompCore | 아니오 |
| 2 | 조인트 · 구동 · 힘 요소 · 출력 + 강체 픽스처 둘 | `동역학_진자` · `동역학_슬라이더크랭크` 를 Exudyn 으로 풀어 판정 안 | CompCore · 해석 쪽 | 아니오 |
| 3 | 화면 — 조건 화면의 동역학 칸 | 조인트를 두 파트 + 좌표계로 고르고 3D 에 축이 보인다, 구동 곡선이 그려진다 | CompCore | 아니오 |
| 4 | 유연체 — `flex` · 접속점 · `flex_bodies[]` + `동역학_유연링크` | SimEngBay 가 만든 축약 유연체로 풀어 판정 안 | CompCore · SimEngBay | 아니오 |
| 5 | Motion 대조 | 세 폴더를 Motion 으로 풀어 Exudyn 과 5 % 안, 틀린 판정은 고친다 | 해석 쪽 → CompCore | 필요 |

- **0단계**: 동역학을 어디서 풀지(SimEngBay 인가 따로인가)는 아직 정하지 않았다(2026-11-01). 그래도
  CompCore 칸은 해석기와 무관하므로 3 ~ 9 는 먼저 정한다 — 칸 이름 · 뜻은 Motion 의 말(12 · 13장)을
  따르고, 칸이 모자라지 않은지는 Exudyn 으로 봤다(14장). 해석 쪽이 정해지면 그쪽은 이 계약을 따르고 안
  맞는 곳만 고친다. 남은 Motion 확인(10장 7)은 라이선스가 있는 운영 서버에서 탐색 스크립트로 한 번에.
- **1단계** 는 작다. `Analysis` 에 `multibody` · `max_time_step`, `end_time` · `output_count` 의
  `only_for` 를 넓힌다. 거동 기본값과 내보낼 때 모든 파트에 `behavior` 를 적는 것, 단위계의 새 차원,
  `mass_properties` 를 물성 밀도 · 단위계로. 11장의 원통면 조각 문제도 여기서 본다.
- **2단계** 가 가장 크다. 모델 셋(`Joint` · `Driver` · `ForceElement`)과 `Output`, 6장의 검증,
  사양표(`spec()` — 화면 · AI 가 읽는다), 점 파일, MCP 안내(`GUIDE.md`). 픽스처 두 폴더는 강체뿐이라
  유연체 없이 계약을 시험한다.
- **3단계**: 칸 대부분은 사양표의 `only_for` 로 그려지므로 작다. 새로 만들 것은 조인트 편집(두 파트 ·
  좌표계 고르기, 3D 의 축 화살표)과 구동 곡선 미리보기다.
- **4단계** 는 SimEngBay 의 유연체 생성을 기다린다. CompCore 쪽은 칸 · 검증 · 열쇠까지 먼저 해 둘 수
  있다.
- **5단계** 는 Motion 이 있는 PC 와 라이선스가 필요하다. 해석 한 건마다 라이선스를 쓰므로 동시 실행
  수는 해석 쪽이 다룬다.

**나중에**: 동역학 접촉, 미리 만든 유연체 파일 참조, 한 스터디에 해석 여럿, 동역학 결과(관절 반력
이력)를 구조 하중으로 잇는 계약.

## 10. 정할 것 — 받는 쪽과

1. **동역학 해석기의 자리** — SimEngBay 안인가, 새 MCP 인가. 결과를 한 곳에서 보려면(ADR 0010)
   SimEngBay 안이 자연스럽다. Motion API 의 Python 3.10 · 3.11 제약은 별도 워커 프로세스로 풀 수 있다.

   SimEngBay 가 MAPDL CMS + DPF 로 쓸 수 있다(13장). Exudyn 으로 갈 때의 형식은 따로 정한다.
3. **칸 이름** — `base` · `action`, 바닥의 이름(`ground`), 1차 조인트 다섯, 구동 `kind` 와 `profile`.
4. **단위** — 각도는 도 · 각속도는 rad/s · 회전 강성은 N·mm/rad 로 섞어 둘지, 구동 · 힘 요소 칸에는

5. **질량 · 관성을 어디에 싣나** — `multibody` 만인가, 모든 해석인가(구조 쪽 메시 질량 점검에도 쓸 수
   있다).
6. **미리 만든 유연체 파일 참조**가 필요한가.
7. **Motion 이 받는 것** — 공개 문서로 풀린 것은 12장, Mechanical 의 Motion 확장으로 풀린 것은 13장.
   남은 것: 모터 토크 결과의 이름과 토크 한계, 리눅스 솔버, 독립 전처리 API(`dfpreAPI`)의 속성 이름이
   Mechanical 확장의 칸 이름과 같은지, `SetMassProperty` 가 받는 곱관성의 부호.
8. **유연체 감쇠의 뜻** — Motion 의 모달 바디는 모드마다 감쇠(`Modes/Damping`)와 강성 비례 감쇠비

   두고, 강성 비례는 필요할 때 칸을 더한다.
9. **스프링 예하중** — Motion 스프링에 `PreLoad` 가 있다(13장). 우리 `spring_damper` 에 칸을 더할지.

  Z = 축), 조인트의 `base` · `action` · `cs`, 구동의 `kind` · `profile` · `unit`, 중력 방향, 해석의
  `end_time` · `output_count` · `max_time_step` 만으로 지었다.
- **평면 기구의 과구속.** 3D 회전 셋 + 미끄럼은 중복 구속이 셋이라 Exudyn 기본 풀이기는 특이 행렬로 멈췄다.
  `EigenDense` + `ignoreSingularJacobian` 으로 풀렸다 — 사람이 조인트를 바꿀 일이 아니라 해석 쪽 설정이다(4장).
- **수치 감쇠.** 일반화 α 의 spectralRadius 1(감쇠 없음)에서는 자리는 맞는데 토크가 한 바퀴마다 50 % 씩
  달랐다. 0.8 에서 맞았다 — 토크 판정이 해석 쪽 설정을 잡아낸다.
- **출발 충격.** 정지에서 정속을 바로 걸면 첫 걸음 토크가 7.09 N·m(정상 최대 0.0067 N·m 의 약 1000 배).
  처음 속도를 맞추면 0.0010 N·m, `ramp` 0.2 s 면 가속 중 0.0134 N·m(실제 관성 토크)였다 — 4장 · 6장.
- **단위.** 점 파일의 질량은 지금 g · g·mm² 이고 조건의 단위계(`mm_n_tonne` 이면 t · t·mm²)와 다르다 —
  1단계에서 단위계로 맞춘다(3장). 이번 시험은 어댑터가 SI 로 바꿨다.
