# 이중화 배포 설계 — 서버 두 대 · 자동 전환

> **얼개는 StandardPlatform 에서 왔다.** 일반적인 설계(왜 메인 서버가 LB 인가, 스플릿 브레인을
> 어떻게 막는가)의 정본은 `../StandardPlatform/docs/이중화-배포-설계.md` 다. 여기는 **이
> 플랫폼의 숫자와 이 플랫폼만의 것**을 적는다 — 운영 절차는
> [deploy/README_OPERATOR.md](../deploy/README_OPERATOR.md) 8장이 정본이고, 여기는 그 뒤의
> 「왜 이렇게 생겼나」 다.

## 1. 구성

```
사용자 · 외부 AI ──HTTPS──▶ 메인 서버 (포탈 + nginx — 메인 서버 쪽이 관리)
                              /compcore/… → 접두어를 벗겨 A · B 로 분배
                         ┌──────────┴──────────┐
                    서버 A                  서버 B      둘 다 활성. 앱 :8060 · MCP :8062
                    PostgreSQL 16 주 ─ 복제 ─▶ 대기     로컬 디스크, 스트리밍 복제
                    DB VIP (있으면) ──────┘              keepalived 가 주를 따라 옮긴다
                         └──── /data/compcore/ 공용 ────┘   작업물 · 백업 · .env
                         └──── 실험계획 공유 폴더 ────┘      해석(ANSYS)이 읽는 자리
```

- **포트는 8060**(개발 8061 · MCP 8062). 플랫폼마다 10씩 벌리는 규칙 안이다 — StandardPlatform
  8040, PartTrace 예약 8050 다음 자리. 이 숫자가 틀리면 같은 서버의 옆 플랫폼과 겹쳐 **나중에 뜬
  쪽이 그냥 못 뜬다.**
- **한 대에 유닛 셋이다** — `compcore`(앱) · `compcore-worker`(작업 워커) · `compcore-mcp`(AI 연동).
  StandardPlatform 과 다른 점은 **워커가 무겁다**는 것이다: 형상 평가 · 지그 생성 · 실험계획이
  전부 거기서 돈다. 두 대 모두 워커를 띄우면 일이 나뉜다(DB 를 큐로 쓰고 `FOR UPDATE SKIP
  LOCKED` 로 집으므로 조정이 따로 없다).
- **단, 두 대가 filestore 를 함께 볼 때만이다.** 공용 `/data` 가 없으면 B 는 클론(대기)이고 워커는 A
  한 대만 돈다 — 3장.
- **`.env` 를 고쳤으면 셋을 함께 재시작한다** — `sudo ./deploy.sh restart`. 앱만 재시작하면 워커와
  MCP 는 옛 설정(특히 옛 DB 주소)을 계속 본다. 무엇이 한 묶음인지는 `./deploy.sh units`.

## 2. 이 플랫폼만의 것 — 실험계획 공유 폴더

`DOE_HOST_DIR`(컨테이너 안에서는 `/data/doe-export`)는 **해석을 도는 쪽이 같은 자리를 보는**
폴더다. 대개 파일 서버의 마운트다.

- **두 대가 같은 경로로 마운트돼 있어야 한다.** 어느 서버의 워커가 그 설계점을 집을지 모른다 —
  한쪽만 마운트돼 있으면 그쪽에서 집힌 작업만 되고, 실패는 「가끔 된다」 로 보인다.
- 백업 대상이 아니다. 주인이 따로 있고, 안의 STEP 은 도면과 설계점에서 다시 만들 수 있다.
- 안 정해도 설치도 DOE 생성도 된다 — 막히는 것은 해석으로 **「내보내기」** 하나다(조용히
  컨테이너 안에 쓰지 않는다 — 그러면 해석 쪽은 영영 못 본다). `install` 이 실제로 써 보고
  말해 준다(`check_doe_dir`).

## 3. 지금의 운영 — 공용 `/data` 가 없어 B 는 클론, 워커는 A 한 대만

**1장의 그림은 목표다.** 운영 서버에는 아직 두 대가 함께 보는 `/data` 가 없다. 그래서 다른 플랫폼
(ReportArchive — 그쪽 `docs/[참고] HWAX포탈_연계_정리.md` §7)과 같이 **포탈 라우트는 A 하나**이고,
B 는 같은 버전 · A 의 DB 를 보며 대기하는 클론이다. 전환은 사람이 한다.

이 모양에서 **B 의 작업 워커는 돌면 안 된다** — 2026-10-07 운영에서 실제로 났다. 워커는 DB 를 큐로
쓰므로(`FOR UPDATE SKIP LOCKED`, 호스트 구분 없음) B 의 워커도 A 의 화면에서 건 작업을 집는다.
그런데 작업의 파일은 서버마다 따로다:

| 흐름 | B 가 집으면 |
| --- | --- |
| 올린 STEP(A 의 `filestore/imports`) → 버전 평가 · 지그 · DOE | `import_step … FileNotFoundError` — B 가 집은 것만 실패. 다시 걸면 또 「반반」 |
| 워커가 만든 STEP · glTF(B 의 `filestore/jobs`) → A 의 다운로드 · 3D | 「작업물 파일이 저장소에 존재하지 않습니다」, 3D 가 빈 칸 |
| 실험계획 서버 보관 폴더(B 의 `filestore/doe`) → A 의 「내보내기」 | 「보관 기한 경과로 정리되었습니다」 가 거짓으로 뜬다. **A 에 옛 사본이 있으면 내보내기가 성공한 척 옛 설계점을 해석으로 보낸다** — 가장 위험하다 |
| 청소 타이머(B) | B 의 반쪽 사본을 보고 「공유 폴더를 치웠다」 를 주 DB 에 적는다 |

그래서 `deploy.sh` 가 **대기(`HA_ROLE=backup`)인데 작업물 폴더가 네트워크 파일시스템이 아니면** 워커와
청소 타이머를 끈 채로 깔고, 그 값(`WORKER_ENABLED`)을 인스턴스 설정에 기억한다 — `update` · `restart` 가
다시 켜지 않게. 유닛은 깔아 두어 전환하는 날 `sudo ./deploy.sh worker on` 한 줄로 켠다. 절차는 운영
가이드 8.1c · 8.3 · 8.4. 판단의 기록은 [ADR 0007](adr/0007-공용-저장소가-없으면-워커는-한-대만.md).

**공용 `/data` 가 생기면** 이 장은 사라진다 — 두 대가 같은 filestore 를 보면 워커가 어디서 집어도 같고,
그때 B 에서 `worker on` 하고 포탈 라우트를 둘로 넓힌다(포탈 생성기가 주소 여럿을 받게 된 뒤).

## 4. DB 와 전환

- PostgreSQL **16**, 두 서버 모두 `prepare` 가 깐다. A 주 · B 대기(스트리밍 복제). 버전이 다르면
  복제가 아예 안 되므로 버전을 박아 깐다.
- 전환은 `/usr/local/sbin/pg-ha`(= `deploy/pg-ha.sh`)가 한다: `db-primary` · `db-standby --from` ·
  `db-promote` · `db-demote` · `db-status`. **계획 전환은 세 명령**(demote → promote → standby)이고
  서버 사이 ssh 를 전제하지 않는다.
- DB VIP 가 있으면 keepalived 가 주를 따라 옮기고 자동 승격까지 간다. 없으면 수동 —
  `db-promote` 뒤 양쪽 `.env` 의 DB 주소를 고치고 `deploy.sh restart`.
- **원복은 사람이 한다.** 승격 뒤 옛 주는 「주 모양의 데이터」 를 들고 있어, 그대로 부팅하면 두
  개의 주가 된다. `pg-ha guard` 가 그것을 막는다(띄우지 않는다).

## 5. 지금 상태 — 무엇이 확인됐고 무엇이 아닌가

| # | 것 | 상태 |
| --- | --- | --- |
| 1 | `ha.sh` · `pg-ha.sh` | StandardPlatform 것과 **한 줄도 다르지 않다**. 그쪽에서 온 것을 그대로 쓴다 |
| 2 | `deploy.sh` 의 이중화 명령 | 있다(`db-*` · `lb` · `render`). 이 플랫폼에 맞춘 것은 유닛 셋과 DOE 폴더뿐 |
| 3 | 번들 빌드 · SIF | **확인됨** — 번들을 만들어 SIF 안에서 CAD 커널이 도는 것까지 |
| 4 | 서버 두 대에서 주/대기 · 전환 | **안 해 봤다.** 코드는 읽고 렌더한 것이지 돌린 것이 아니다 |
| 5 | 대기 서버의 워커 끄기(`WORKER_ENABLED` · `worker on/off`) | `render` 로 단독 · 주 · 대기 · 명시 네 경우를 확인. 운영 B 에서 `update` 로 꺼지는 것은 다음 배포 때 |

4 번이 첫 설치의 리허설이다. 순서는 운영 가이드 8장 그대로:
A 설치 → B 설치 → 한 대 정지 → 주 DB 정지 · B 승격 → 옛 주를 대기로 → 재부팅 점검.
**그 전에 `deploy.sh render` 로 root 없이 유닛 · nginx 조각 · keepalived 설정을 눈으로 본다** —
서버에서 처음 만드는 것보다, 만들어질 것을 먼저 보는 편이 싸다.
