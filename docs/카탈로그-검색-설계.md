# 카탈로그 검색과 태그 — 계획

> 2026-09-24. 5단계에서 「필요해질 때」 로 미뤄 둔 것. **이제 필요해지는 까닭**이 셋 생겼다:
> DOE 가 읽기 공개가 되어 남의 이력을 찾을 수 있게 됐고, 오케스트레이터가 카탈로그를 뒤져
> 고르게 되고, 등록한 부품에 **태그가 사라지고 있다**(아래 ①).

## 0. 지금 있는 것 — 생각보다 많다

| 어디 | 검색 | 태그 | 화면 |
| --- | --- | --- | --- |
| 내 작업 | `q`(이름 · 설명) · `kind` · 휴지통 | ✅ `works.tags` · `GET /works/tags` | ✅ 검색 입력란 + 태그 칩 |
| 부품 | `q`(이름 · 설명) | ❌ **칸이 없다** | ❌ 검색 입력란 없음 |
| 지그 | `q`(이름 · 설명) | ❌ | ❌ |
| 템플릿 | `q`(이름 · 설명) | ❌ | ✅ 검색 입력란 |
| DOE | ❌ | ❌ | ❌ (`scope=all` 만 2026-09-24) |

**백엔드는 절반쯤 돼 있고 화면이 덜 붙었다.** 그러니 이 일은 「검색을 만든다」 가 아니라
**「있는 것을 고르게 이어 붙이고, 빠진 칸 하나를 더한다」** 다.

## 1. 왜 지금인가 — 세 가지

### ① 등록하면 태그가 사라진다 (버그에 가깝다)

`works.tags` 는 내 작업에만 있다. 등록(`promote`)은 `Part(name=…, description=…)` 만 만들고
**태그를 안 옮긴다**(`works/services.py`). 사람이 「브래킷 · EMC · 2026」 이라고 붙여 둔 것이
공용 공간으로 나가는 순간 없어진다 — 정작 남이 찾아야 하는 자리에서.

### ② DOE 가 읽기 공개가 됐다

`scope=all` 로 남의 DOE 를 볼 수 있게 했는데(2026-09-24), **검색할 방법이 목록 넘기기뿐**이다.
「같은 훑기를 다시 도는 것이 가장 큰 낭비」 라고 해 놓고 검색할 길을 안 준 셈이다.

### ③ 오케스트레이터가 고른다

기계는 목록을 넘기지 않는다. `search` MCP 도구가 있지만 이름 · 설명만 본다 — 「M6 볼트 구멍이
있는 판」 같은 물음에 답하지 못한다.

## 2. 무엇을 만드나

### A. 태그를 **등록 너머로** 잇는다 ✅ 완료 (2026-09-24)

- `parts` · `jigs` · `recipe_templates` 에 `tags` 칸(JSONB, works 와 같은 모양).
- 등록이 `work.tags` 를 그대로 옮긴다. 이미 등록된 것은 마이그레이션이 원본 작업에서 채운다
  (`work_id` 가 살아 있다).
- 카탈로그 목록에 `?tag=` 와 `GET /parts/tags` — **works 와 똑같은 모양**으로. 화면도 같은
  컴포넌트를 쓴다(내 작업의 태그 칩을 빼서 공용으로).

**이것만으로 ①이 없어지고**, 나머지는 그 위에 얹는다.

**된 것**(2026-09-24):

- 마이그레이션 0020 — 세 테이블에 `tags`. **있던 줄은 `work_id` 로 원본에서 채웠다**
  (작업을 지운 것은 이미 못 살린다 — 늦을수록 못 살리는 것이 늘어서 먼저 했다).
- 등록이 물려받는다. **버전을 올릴 때도 따라온다**(첫 등록 뒤에 더한 것도 와야 한다).
  다만 카탈로그에서 뺀 것을 복원하지는 않는다 — 거기서 지운 것은 뜻이 있다.
- `?tag=` 와 `GET /{parts,jigs,templates}/tags` — **내 작업과 같은 모양**이다.
- 화면: `TagFilter` 하나를 넷이 쓴다(내 작업의 것을 빼서 공용으로). 태그가 없으면
  아무것도 안 그리고, 목록이 아닌 것이 와도 페이지가 죽지 않는다.

템플릿은 `work_id` 가 없어 채울 원본이 없다 — 칸만 만들고 앞으로 저장하는 것부터 붙는다.

### ✅ B. 검색을 **한 모양**으로 (2026-10-03)

지금 `q` 는 모듈마다 따로 쓴 `ILIKE %q%` 다. 같은 규칙을 한 곳에 둔다:

- **무엇을 보나**: 이름 · 설명 · **태그** · 작성자. 낱말마다 나눠 AND(MatNexus 가 그렇게
  한다 — 「알루미늄 5052」 가 둘을 다 든 것을 찾는다).
- `pg_trgm`(쓸 수 있음을 확인했다) + `GIN` 인덱스. `ILIKE %q%` 는 인덱스를 못 타는데,
  트라이그램은 탄다. **한글이 섞여도 된다** — Postgres 의 전문 검색은 한국어 사전이 없어서
  형태소로 못 쪼개지만, 트라이그램은 글자 단위라 상관없다.
- **지금은 필요 없다**(부품 0 · 지그 0 · 작업 12줄). 인덱스는 **B 를 하는 김에** 같이 넣되,
  이것을 하는 까닭은 속도가 아니라 **규칙이 한 곳에 있는 것**이다.

**된 것**(2026-10-03): `backend/app/shared/search.py` 의 `matches()` 하나 — 낱말마다 AND, 낱말은
이름 · 설명 · 태그(`tags::text`) · 작성자(표시 이름) 어디에 있어도 된다(OR). `%` · `_` 는
글자로 묶는다. 내 작업 · 부품 · 지그 · 템플릿 · DOE 의 `q` 가 다 이것을 부르고, 목록마다 덧붙이는
것은 `also` 로(지그는 **부품 이름**, DOE 는 **대상 작업 이름**). 마이그레이션 0028 이
`pg_trgm` 과 GIN 색인(표마다 name · description · `(tags::text)`)을 만든다 — 확장을 만들 권한이
없는 DB 면 색인 없이 지나간다(답은 같다). 모델의 `__table_args__` 에도 적어 `alembic check` 가
어긋나지 않는다. MCP `search` 는 같은 API 를 부르므로 그대로 태그 · 작성자까지 본다.

### ✅ C. DOE 를 검색할 수 있게 (2026-10-03)

`GET /doe` 에 `q`(이름 · 설명 · **대상 작업 이름** · 작성자)와 `tag`(**대상 작업의 태그** —
DOE 에는 태그가 없다), `GET /doe/tags?scope=` 가 보이는 DOE 들의 대상 작업 태그를 준다.
화면은 「내 항목 / 전체」 토글 옆에 검색 입력란과 태그 칩. MCP `doe_studies(query, tag)`.

### ✅ D. 형상으로 검색 — ① 레시피로 + ② 치수로 (2026-10-03)

「M6 구멍이 있는 판」 · 「두께 변수가 있는 지그」. 레시피는 JSONB 이므로 **쓰인 연산과 변수
이름**을 뽑아 두면(`ops: ["box","hole"]` · `params: ["두께","길이"]`) 그걸로 필터링할 수 있다.
평가할 때 한 번 뽑아 버전에 적어 두면 질의는 거저다.

**이것이 오케스트레이터에게 가장 쓸모 있지만 가장 크다.** A · B · C 가 끝나고, 실제로 「못
찾겠다」 는 말이 나온 뒤에 한다 — 안 그러면 아무도 안 쓰는 색인을 만든다.

**한 것(2026-10-03, 사용자가 앞당김):** 색인은 버전이 아니라 **그 버전을 평가한 작업의 요약**
(`jobs.summary.shape`, `core/shape_index.py`)에 적는다 — CAD 평가와 지그 생성이 끝날 때 한 번.
레시피에서 연산 · 나사 호칭 · 변수 이름(①), 형상에서 경계상자 · 작은 것부터 늘어놓은 세 변 ·
부피 · 솔리드 수 · 구멍(지름으로 묶어 개수 · 그중 관통, `core/drawing.holes` 를 솔리드마다)(②).
목록(`/works` · `/parts` · `/jigs`)은 **최신 버전만** 본다 — 그 항목의 현재 버전 → 그 버전의
작업 요약을 `EXISTS` 로 따라간다(`shared/shape_search.py`). 조건: `has`(구멍 · 판금 · 프레임 …
여러 연산을 한 낱말로) · `thread` · `param` · `fits`(「이 상자 안에」 — 방향 무관, 두 변이면 큰
두 변만) · `volume_min/max` · `hole`(± `hole_tol`) · `holes`. 목록 한 줄에 `shape` 가 붙는다.
이 기능 전의 버전은 관리자가 서버 화면 「형상 색인 생성」 으로 남긴 STEP 에서 채운다
(`POST /server/shape-index`). 화면: 세 목록의 「형상」 필터, MCP `find_by_shape`.
**③ 유사 형상(2026-10-03)**: `POST /search/similar` — `source`(`work:` · `part:` · `jig:` 의 최신
버전) 또는 저장 전 `recipe` 와 유사한 것을 점수 순으로. 점수는 형상 색인의 성분별 유사도의 무게 합
(`core/shape_index.similarity`): 크기(작은 것부터 늘어놓은 세 변의 로그 비) 0.30 · 비율(긴 변에
대한 두 변 — 크기가 달라도 모양이 같으면 높다) 0.15 · 체적 충전율(부피 / 경계상자 — 판 · 브래킷 ·
프레임을 가른다) 0.15 · 구멍(지름 ± 0.5 mm 로 짝지은 개수의 가중 자카드) 0.25 · 쓴 연산(자카드,
둘 다 레시피가 있을 때만) 0.10 · 솔리드 수 0.05. 없는 성분은 빼고 남은 무게로 나눈다. 줄마다
「왜」(크기 유사 · 구멍 동일 · 형상 비율 동일(크기 다름) …)를 붙여 점수만 보고 고르지 않게 한다.
가장 긴 변이 네 배 넘게 다른 것은 SQL 에서 먼저 거르고, 같은 버전(작업에서 등록한 부품)은 뺀다.
**유사한 부품에는 그 부품의 지그**를 붙인다 — 지그를 새로 만들기 전에 다시 쓸 길이다. 화면은
부품 · 지그 · 작업 화면의 「유사 형상」 카드, MCP `find_similar`.

## 4. 정하지 않은 것

- **태그를 누가 정하나.** 지금은 자유 입력이다. 자유롭게 두면 「브래킷」 · 「브라켓」 ·
  「bracket」 이 갈라진다. 사전을 둘지, 쓰던 것을 먼저 보여 주는 것으로 족한지
  (`GET /works/tags` 가 이미 그 일을 한다) — **후자로 시작하고 갈라지는 것을 보고 정한다.**
- **공용 카탈로그의 태그를 누가 고치나.** 등록한 사람만인가, 아무나인가. 공용 공간이라
  「아무나」 가 맞아 보이지만, 그러면 태그 편집 이력이 필요해진다.
- **D 의 색인을 버전마다 두나 작업마다 두나.** 버전마다가 정확하지만 줄이 는다.
