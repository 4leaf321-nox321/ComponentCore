# 0011. 태그는 온톨로지의 객체다 — 붙이면 어휘가 쌓인다

날짜: 2026-10-23
관련: [ADR 0008](0008-온톨로지와-그-기반을-StandardPlatform-에서-들인다.md) · `backend/app/modules/tagging` ·
`backend/app/modules/works/system.py` · 마이그레이션 0037

## 결정

작업 · 부품 · 지그의 태그는 글자가 아니라 **온톨로지의 객체**다. 붙인 것은 선(`object_links`, 관계
`cc_tagged`)이고, 작업 · 부품 · 지그는 원 표(`kind_class='system'` 타입 — `cc_work` · `cc_part` ·
`cc_jig`)로 비춘다. `works` · `parts` · `jigs` 의 `tags` 칸은 지웠다(템플릿은 그대로다).

- **태그 타입은 관리자가 고른다**(관리 › 온톨로지 › 태그, 표 `tag_types`). 「고르기」 는 있는 객체에서
  고르기만, 「고르기 · 늘리기」 는 **붙이는 사람 누구나** 그 타입에 새 객체를 만든다. 늘리기여도 그
  타입의 규칙이 막으면(허브가 관리 · 입력 정책 닫힘 · 식별자 필수 · 채울 칸) 만들지 않는다.
- **기본은 「일반 태그」(`cc_tag`, 늘리기)** — 타입을 안 고르면 거기다. 끌 수 없다.
- **태그 객체는 전역**(부서 소유가 아니다)만 붙고 보인다. 붙이는 사람이 만든 객체도 전역이고
  감사 기록(`object.create`, 까닭 「태그로 만듦」)에 남는다.
- 붙이고 떼는 사람은 **그 행을 고칠 수 있는 사람**이다 — 작업은 주인, 부품 · 지그는 올린 사람과
  시스템 관리자. 떼도 객체는 남는다.
- **글자 목록으로 주고받는 길은 남긴다.** 목록 · 상세의 `tags` 는 붙은 객체의 이름, `?tag=` 는 그
  이름으로 거른다, `PATCH /works/{id}` 의 `tags`(MCP `update_work` · 시편 · 규격 묶음)는 이름마다
  이미 붙은 것을 두고 없는 것은 「일반 태그」 에서 찾거나 만든다.

## 배경

2026-10-23 「지금 온톨로지와 태그 시스템이 정확히 어떻게 되는가」 를 물었을 때 둘은 따로였다. 태그는
행마다 적은 글자 목록이라 같은 말을 사람마다 달리 적고(「굽힘시험」 · 「굽힘 시험」), 그 말이 프로젝트인지
고객사인지 아무도 몰랐다. 온톨로지는 부품 · 지그를 원 표로 비추지만 **도면(작업)에 잇는 길이 없었다.**
「태그를 쓸 때 온톨로지의 타입을 고르고 그 안에서 고르거나 늘려서, 태그로 온톨로지 데이터가 자연스럽게
쌓이게」 하자는 요청이 나왔다.

## 대안

- **A. 글자 칸을 두고 이름을 사본으로 적는다**(선이 정본, 칸은 캐시). 목록 · 찾기 코드를 안 고친다.
  하지만 온톨로지 화면에서도 선을 잇고 끊고, 객체 이름을 고치고 합친다 — 사본은 반드시 갈린다. 버렸다.
- **B. CompCore 전용 표(`tag_links`)에 둔다.** 비공개 작업이 원 표가 될 필요가 없다. 대신 그 선은
  온톨로지 그래프 · 경로 · 객체 상세에 안 보인다 — 「도면에 잇는 길」 이 여전히 없다. 버렸다.
- **C. `object_links` 의 선이 정본, 작업도 원 표**(택함).

## 작업을 원 표로 열며

작업은 내 공간이다 — 주인과 시스템 관리자만 본다. 그런데 들인 원 표 계약(`SystemSource`)의 `lookup` ·
`list_all` 은 보는 사람을 받지 않고, 그래프 · 묶음 내보내기 · 상세의 관련 객체가 그것을 부른다. 그 자리를
다 고치면 SP 와 견줄 수 없게 된다. 그래서 작업 원 표는 **요청의 사람**으로 거른다 — 인증이 끝나면
`request_context.set_viewer` 가 적고(포털 위임 토큰이 관리자 표시를 내린 뒤의 값), 요청 밖(작업 · 스크립트)
이면 작업은 하나도 안 나온다. 선의 감사 기록에는 작업 이름 대신 「작업」 이라고만 적는다 — 그 기록은
태그 객체의 이력 · 지켜보기 알림 · 웹훅으로 나가고, 그쪽을 보는 사람은 남의 작업을 못 본다.

## 결과

- 태그 객체를 온톨로지에서 열면 「태그가 붙은 것」 이 보인다(남의 작업은 빼고). 그래프 · 경로가 그 선을 탄다.
- 기준정보 칸(부품 · 지그 화면, `objects/source_links.py`)은 태그 관계를 줄로 세우지 않는다 — 제 자리가 있다.
- 마이그레이션 0037 이 옛 꼬리표를 옮겼다: 이름마다(공백을 하나로, 대소문자 무시) 「일반 태그」 객체 하나,
  행마다 붙어 있던 순서대로 선 하나. 되돌리면 칸을 되살리고 선에서 이름을 다시 채운다.
- 기본 정의(원 표 타입 셋 · 「일반 태그」 · 태그 관계)는 앱이 처음 쓸 때도 만든다(`tagging.services.ensure`)
  — 시험은 마이그레이션이 아니라 `create_all` 로 표를 세운다. 관리자가 같은 원 표를 비추는 시스템 타입을
  이미 만들어 두었으면 그것을 쓴다.
- 「내 작업의 태그만」 자동 완성(`GET /works/tags`)은 이름 목록으로 남았다(MCP `list_tags`). 붙이는 자리의
  후보는 그 타입의 객체 전부(많이 쓴 순)다 — 태그는 이제 모두의 어휘다.
- **목록 거르개는 객체로**(2026-10-25): 작업 · 부품 · 지그 · DOE 목록의 `?tag_id=` — 이름이 같은 다른
  타입의 태그(고객사 A · 프로젝트 A)가 갈린다. 칩은 `GET /api/tags/used/{target}`(DOE 는
  `/api/doe/tag-objects`)이 타입별로 준다. 이름 거르개(`?tag=`)는 MCP 를 위해 남는다.
- **템플릿도 같다**(2026-10-26, 마이그레이션 0038): 템플릿 원 표(`templates/system.py`, cc_template) —
  공용이 아닌 템플릿은 주인만 보므로 작업처럼 요청의 사람으로 거르고, 선의 감사 기록에 이름을 안
  남긴다. 템플릿은 지우면 행이 사라지므로 붙은 선도 함께 지운다(`tagging.forget`).
- **비슷한 태그 정리**(2026-10-26): 「늘리기」 로 쌓인 어휘는 띄어쓰기 · 이음표만 달리 갈린다(「굽힘시험」 ·
  「굽힘 시험」 — 붙일 때의 같은 이름 찾기는 대소문자만 무시한다). 관리 › 온톨로지 › 태그의 「비슷한 태그
  정리」(`GET /api/tags/similar`, MCP `tag_similar`)가 같은 타입 안에서 비교키에서 띄어쓰기 · 이음표를 뺀
  것이 같은 묶음과 남길 것의 추천(많이 쓴 것 → 식별자 → 먼저 만든 것)을 보이고, 사람이 고른 것만
  합친다(`POST /api/tags/merge`, MCP `tag_merge`). 합치기는 온톨로지의 객체 합치기(`lifecycle.merge_into`)
  그대로라 붙은 선이 옮겨 가고, 지운 이름은 남긴 것의 별칭이 되어 같은 표기로 다시 붙여도 남긴 것으로
  풀린다. 규칙을 넓히지 않았다(구두점 · 비슷함 점수) — 「포스코(주)」 처럼 뜻이 있는 표기를 기계가 묶지 않게.
  규칙에 안 걸리는 것은 객체 화면의 「합치기」 로.
