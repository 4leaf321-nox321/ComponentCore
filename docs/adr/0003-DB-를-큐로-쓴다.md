# 0003. 작업 큐는 DB(PostgreSQL) 다 — 별도 큐 서버를 두지 않는다

날짜: 2026-09-18

## 결정

모든 "만드는 일" 은 `jobs` 표의 행이다. 워커는 `SELECT … FOR UPDATE SKIP LOCKED` 로 `queued` 행을
집어 `running` 으로 바꾸고 돌린다. Redis · RabbitMQ · Celery 를 쓰지 않는다.

## 배경

[0002](0002-지그-생성은-동기로-돈다.md) 는 동기로 두었다. 로드맵 2~4단계(레시피 평가 · AI 편집)는
수십 초가 걸리는 일이라 요청 안에서 돌릴 수 없고, 1단계에서 큐가 들어왔다.

큐가 필요한 것은 맞지만 큐 **서버**가 필요한 것은 아니다. 작업이 분당 몇 건이고, 사내 설치는
Apptainer 단일 이미지 + PostgreSQL 이다. 큐 서버를 더하면 설치 · 백업 · 감시 · 장애 지점이 하나
더 생긴다.

## 대안

- **Celery + Redis** — 재시도 · 스케줄 · 모니터링이 있지만 Redis 를 설치 · 운영해야 한다. 작업이
  시간당 수천 건이 되면 그때 옮긴다 — `jobs` 표는 그대로 두고 집는 쪽만 바뀐다.
- **FastAPI BackgroundTasks** — 같은 프로세스에서 돌아 워커를 따로 늘릴 수 없고, 서버를 재시작하면
  돌던 작업이 사라진다. 기각.

## 결과

- `app/modules/jobs` — 표 · 레지스트리 · 서비스. 종류는 `app/handlers.py` 에서 등록한다.
- `app/worker.py` — 폴링 1초. 30분 넘게 `running` 인 작업은 워커가 죽은 것으로 보고 되살린다
  (2번째까지). 개발에서는 `run.py` 가 자식으로 하나 띄운다.
- `JOBS_INLINE=1` — 워커 없이 요청 안에서. 시험과 워커를 안 띄우는 작은 설치.
- 작업의 `input` 은 스냅숏이다 — 프로젝트가 바뀌어도 작업 기록은 그대로다.
