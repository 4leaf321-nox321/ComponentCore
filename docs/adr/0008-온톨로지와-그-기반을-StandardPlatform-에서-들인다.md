# 0008. 온톨로지 · 객체와 그 기반을 StandardPlatform 에서 들이고, SP 의 기준정보를 받는다

날짜: 2026-10-13
관련: [ADR 0001](0001-StandardPlatform-에서-구조만-가져온다.md)(구조만 가져온다) — 그 「가져오지 않은 것」
가운데 부서 · 온톨로지 · 객체 · 알림 · 데이터 소스를 **뒤집는다.**

## 결정

CompCore 에 StandardPlatform(이하 SP)의 **온톨로지 모듈을 거의 그대로** 들인다 — 타입 · 속성 ·
관계를 데이터로 정의하면 목록 · 상세 · 트리 화면이 생기는 메타모델과 그 위의 객체 · 관계 · 그래프 ·
찾기, 그리고 그것이 서 있는 기반(부서 · 권한 · 감사 기록 · 첨부 · 알림)이다. 그 위에서 두 길을 연다:

1. **받기** — SP 가 바깥에 공개한 기준정보(`/api/core`)를 주기적으로 당겨 이 온톨로지에 쌓는다.
   SP 코어 연동 키트(`coreapi/kit/sp_core_pull.py`)가 정한 수신 규칙(증분 · 삭제 · 병합 · 숨김 ·
   처음부터 다시 받기 · 관계)을 그대로 지킨다.
2. **쓰기** — CompCore 의 기능(작업 · 부품 · 지그 · DOE)이 그 객체를 가리키고 값을 읽는다.

옮기는 원본은 SP `6e5a773`(v0.4.51)이다. 모듈 이름 · 표 이름 · 화면 경로는 SP 와 **같게** 둔다 —
나중에 SP 의 개선을 받을 때 파일끼리 견주기 쉽게. 오류 코드 접두어만 이 플랫폼의 것(`CCR`)이다.

## 배경

ADR 0001 은 「지그 생성의 핵심은 기하 파이프라인이고 부서 · 온톨로지와 무관하다」 로 이것들을 뺐다.
그 판단은 지그 생성에는 여전히 맞다. 바뀐 것은 **CompCore 가 혼자 쓰이지 않게 된 것**이다 — 해석
(SimEngBay) · 물성(MatNexus) · 기준정보(SP)와 이어지고, 제품 · 고객사 · 프로젝트 · 시험 항목 같은
기준정보를 플랫폼마다 따로 적으면 **반드시 갈린다.** SP 의 코어 API 는 바로 그 기준정보를 한 곳에서
내보내려고 만든 창구이고, 받는 쪽에도 같은 모양(타입 · 속성 · 관계)이 있어야 받은 것을 잃지 않는다.

## 대안

1. **필요한 표 몇 개만 손으로 만들기**(제품 · 고객사 표) — 빠르지만 SP 의 타입이 하나 늘 때마다
   여기에 표 · 화면 · 마이그레이션을 다시 쓴다. ADR 0005(SP)가 「코드를 쓰는 일을 데이터를 채우는
   일로」 바꾼 이유가 그대로 여기에도 온다. 기각.
2. **SP 의 핵심(정의 · 객체 · 화면)만** — 사용자가 「거의 그대로」 를 골랐다(2026-10-13). 핵심만
   옮기면 일괄 입력 · 데이터 소스 · 검토함 같은 주변이 나중에 다른 모양으로 붙어 SP 와 갈린다.
3. **CompCore 를 SP 의 인스턴스로 다시 세우기** — ADR 0001 의 기각 이유(OCP 가 든 무거운 이미지,
   틀의 규칙을 지우면서 시작)가 그대로다. 기각.

## 지키는 것

- **작업 큐는 둘, 워커는 하나.** SP 의 작업(DB 세션을 들고 도는 「계획 → 확정 → 적용」)은 CompCore 의
  작업(`jobs` — 웹 · DB 를 모르는 실행 함수가 형상을 만든다)과 **칸의 뜻이 다르다**: 진행률이 사전 대
  단계 목록, 결과가 `result` 대 `summary`, 계획과 적용을 잇는 부모 작업 · 입력 파일. 한 표에 두 뜻을
  섞으면 화면과 워커가 둘 다 갈린다. 그래서 SP 의 것을 **`tasks`(데이터 작업)** 로 들인다 — 모듈 ·
  표 · 경로 이름만 바꾸고(`jobs` → `tasks`) 코드는 그대로. 워커 프로세스는 하나가 둘을 번갈아 집는다
  (배포의 워커 유닛 · ADR 0007 의 「워커는 한 대만」 이 그대로 선다).
- **이름이 겹치는 것은 SP 쪽을 바꾼다** — `jobs` → `tasks`, `search`(전체 찾기) → `objectsearch`.
  `audit` · `accounts` · `auth` · `server` 는 CompCore 의 것에 SP 가 쓰는 칸 · 함수를 더한다.
- **기존 자료의 권한은 그대로.** 작업 · 부품 · 지그 · DOE 는 지금처럼 사람(소유자 · 관리자)으로
  판정한다. 부서가 소유하는 것은 온톨로지 객체부터다 — 기존 자료에 부서를 붙이는 것은 그것이 필요해진
  날 따로 정한다(로드맵 「부서 단위 공개 범위」).
- **기본 부서는 만들지 않는다**(2026-10-13 바꿈 — 처음에는 「기존 사용자는 기본 부서로」 였다).
  SP 에서 객체를 만드는 것은 그 부서의 **관리자**라, 모두를 멤버로 넣어도 객체를 만들 수 있는 사람은
  생기지 않는다. 부서는 시스템 관리자가 「관리 › 부서 정보」 에서 만들고 사람을 넣는다. 소속이 없는
  사람에게는 부서 선택기 · 부서 스코프 메뉴가 안 선다 — 형상 작업만 하는 사람의 화면은 그대로다.
- **CompCore 의 부품 · 지그는 온톨로지의 원 표다**(`kind_class='system'`, `parts/system.py` ·
  `jigs/system.py`). 행을 복제하지 않는다 — SP 에서 받은 제품 · 프로젝트가 부품 **그 자체**를 관계로
  가리키고, 부품 · 지그 상세의 「기준정보」 카드가 그 선을 보인다. 작업(내 작업) · DOE 는 주인만 보는
  것이라 원 표로 열지 않는다(보는 사람으로 거르지 않는 참조 이름 풀이가 남의 것을 드러낸다).
  **2026-10-23 바뀜**: 작업 · 템플릿은 태그를 잇기 위해 원 표가 됐고, 요청의 사람으로 걸러 그 문제를
  막는다([ADR 0011](0011-태그는-온톨로지의-객체다.md)). DOE 는 그대로다.
- **부품 · 지그 화면에서 잇는 선은 그 부품(지그)을 고칠 수 있는 사람이 잇는다**(2026-10-14,
  `objects/source_links.py`). SP 의 규칙은 「출발점을 고칠 수 있는 사람」 인데, 받은 기준정보는
  「기준정보」 부서 소유라 그대로면 부품을 만든 설계자가 제 부품에 적용 모델을 못 단다. 선의 방향
  (기본 모델 → 부품)은 관계 정의대로 두고 권한만 부품 쪽에서 본다. 카드의 칸은 코드에 박지 않는다 —
  원 표 타입에 닿는 관계 종류마다 한 줄이 선다.
- **화면 경로는 SP 와 같다** — 동적 화면은 `/o/:typeSlug` · `/o/:typeSlug/:id` 둘이고, 정적 화면의
  정본은 여전히 `navigation.ts` 다(SP ADR 0005 결정 2).

## 결과

- 단계와 순서는 [온톨로지-이식-계획.md](../온톨로지-이식-계획.md) — 기반 → 정의 → 객체 → SP 수신 →
  CompCore 기능 연결 → 나머지(데이터 소스 · 검토함 · 묶음 · RDF · 웹훅 · 지표 · MCP).
- `AGENTS.md` 의 「StandardPlatform 의 인스턴스(… 온톨로지 · 부서)가 아니다」 는 「인스턴스는
  아니지만 온톨로지 · 부서는 들였다」 로 고친다. 확장 모듈 기제(`EXTENSIONS`)는 여전히 들이지 않는다.
- 이미지 · DB 가 커진다(표 수십 개). OCP 와 달리 순수 파이썬 · SQL 이라 배포 형태는 그대로다.
