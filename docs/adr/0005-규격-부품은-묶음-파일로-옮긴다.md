# 0005. 규격 부품은 묶음 파일로 옮긴다 — 가져오기는 카탈로그 버전을 바로 만든다

날짜: 2026-10-04

## 결정

개발 PC 에서 그린 규격 부품을 **묶음 파일**(JSON 하나, `compcore.standard-parts` 판 1)로 내보내고
운영 서버에서 가져온다. 둘 다 **시스템 관리자만** 한다(`POST /parts/standard/export` ·
`POST /parts/standard/import`).

- 묶음의 항목 하나 = 카탈로그 정보(이름 · 설명 · 폴더 · 태그) + 사양(쓰는 버전 빼고) + **쓰는
  버전의 레시피** + 출처(내보낸 서버의 부품 id · 버전).
- 가져오기는 **품번으로 짝짓는다.** 없으면 새 부품 v1, 있으면 형상(레시피)이 다를 때 새 버전 ·
  사양만 다르면 사양만 고친다. 같으면 그대로 둔다. 이름 · 설명 · 폴더 · 태그는 새로 만들 때만 쓴다.
- 항목마다 사양 · 형상 기준(`_standard_problems`)을 본다. 어긴 항목은 건너뛰고 까닭을 말한다 —
  나머지는 가져온다. `dry_run` 이 먼저 할 일을 보여 준다(화면은 늘 미리 보기 → 확인).
- 가져온 버전은 **내 작업을 거치지 않는다.** 부품 버전을 바로 만들고(`work_version_id` 없음,
  메모에 출처) 평가 작업(`cad`)을 걸어 STEP · glTF 를 만든다.
- 품번은 규격 부품 사이에서 **하나**다 — 사양을 붙일 때도 막는다(PARTS-0011). 짝짓는 열쇠라서.

## 배경

규격 부품(받침 · 위치 핀 · 토글 클램프)은 사내에서 그려 관리자가 사양을 붙인다(2026-10-04). 그리는
곳은 개발 PC 이고 쓰는 곳은 운영 서버다. 운영에서 같은 것을 다시 그리고 사양을 손으로 옮겨 적으면
품번 · 치수가 어긋난다. 사용자는 「개발 PC 에서 몇 개 골라 내보내고 운영에서 가져오는」 길을
요청했다.

## 대안

- **운영에서 내 작업으로 만들고 등록**(지금의 길 그대로) — 등록은 평가가 끝나야 해서(`_done_job`)
  가져오기가 「작업 만들기 → 평가 기다리기 → 등록 → 사양」 의 두 단계 비동기가 된다. 관리자의
  내 작업에 규격품 작업이 수십 개 쌓이기도 한다. 기각 — 규격품은 개발 PC 에서 고쳐 다시 옮긴다.
- **DB 덤프 · 표 복사** — 부품 id · 사용자 id 가 서버마다 달라 맞지 않고, 다른 부품까지 딸려 간다.
  기각.
- **STEP 으로 옮기기** — 규격품은 레시피로만 그린다(변수로 높이 · 길이를 맞춘다). STEP 으로는 그
  변수가 사라진다. 기각.
- **문제가 하나라도 있으면 묶음 전체를 거절** — 예측은 쉽지만 수십 개 중 하나 때문에 나머지를
  못 옮긴다. 미리 보기가 건너뛸 것을 먼저 보여 주므로 건너뛰기로 했다.

## 결과

- 「남에게 공개하는 유일한 길은 등록」(AGENTS.md)의 **예외 하나**: 관리자의 규격 부품 가져오기.
  관리자만이고, 들어오는 레시피는 STEP · 다른 도면을 가리킬 수 없다(형상 기준이 거절한다).
- 화면: 부품 목록에서 관리자가 고른 규격 부품을 「규격 부품 내보내기」, 「규격 부품 가져오기」 창이
  미리 보기 표(새 부품 · 새 버전 · 사양 수정 · 변경 없음 · 건너뜀)를 보여 주고 확인받는다.
- MCP: `export_standard_parts` · `import_standard_parts`(기본 `dry_run`).
- 같은 묶음 형식으로 규격표에서 만든 규격품을 한꺼번에 들일 수 있다 — 표에서 묶음을 만드는
  스크립트를 쓰면 개발 · 운영에 같은 파일을 가져온다.
