# 0002. 지그 생성은 (지금은) 요청 스레드에서 동기로 돈다

날짜: 2026-09-17 · **2026-09-18 에 [0003](0003-DB-를-큐로-쓴다.md) 으로 대체됨** — 로드맵 1단계에서
작업(Job) · 워커가 들어오면서 생성은 큐로 걸린다. 여기 적은 「표를 처음부터 비동기에 맞게」 는
그대로 쓰였다.

## 결정

`POST /api/jigs/projects/{id}/runs` 는 파이프라인을 다 돌리고 끝난 결과(성공 · 실패)를 돌려준다.
큐 · 워커 · 폴링은 두지 않는다.

## 배경

손바닥만 한 부품(100mm 급, 면 수십 개)은 전 단계가 0.3초 안쪽이다(실측: 시연 브래킷 307ms,
그중 export 83ms · interference 59ms). 큐를 두면 워커 프로세스 · 상태 폴링 · 실패 재시도가 따라오고,
그것은 지금 아무도 겪지 않는 문제를 위한 비용이다.

## 대안

- **FastAPI BackgroundTasks** — 응답은 빨라지지만 같은 프로세스에서 돌아 워커 수(uvicorn
  workers)가 곧 동시 실행 수인 것은 같다. 상태 폴링만 더해진다. 보류.
- **별도 워커(큐)** — 큰 조립체 · 정밀 간섭 검사가 들어오면 필요하다. 그때 `jigs/services.execute_run`
  이 워커가 부르는 함수가 되고, `JigRun.status = running` 이 이미 있어 화면은 폴링만 더하면 된다.

## 결과

- `uvicorn_workers` 기본값을 2 로 둔다 — 워커 수가 동시 생성 수다.
- `JigRun` 에 `status` 와 `started_at` · `finished_at` 을 처음부터 두어 비동기로 옮길 때 표가
  안 바뀌게 했다.
