# 0001. StandardPlatform 에서 구조만 가져오고 독립 플랫폼으로 세운다

날짜: 2026-09-17

## 결정

AutoJigGenerator 는 StandardPlatform 의 **인스턴스(확장 모듈)가 아니라 별도 저장소**다.
StandardPlatform 에서는 로그인(JWT + 회전하는 refresh 쿠키) · 설정(`.env` → `Settings`) · 오류
봉투와 요청 ID · 접근 로그 · 파일 저장소 · 한 프로세스가 SPA 까지 서빙하는 배포 형태 ·
프론트 껍데기(사이드바 · 오류 경계 · shadcn 프리미티브)만 가져왔다.

가져오지 않은 것: 확장 모듈 기제(`EXTENSIONS`), 부서(workspaces), 온톨로지 · 객체, 공지 ·
알림 · 웹훅 · 데이터 소스, PAT(개인 토큰), 가입 승인 흐름.

## 배경

StandardPlatform 은 「도메인이 무엇이든 매번 다시 만들게 되는 것」 을 모아 둔 틀이고, 도메인은
확장 모듈로 얹게 되어 있다. 지그 생성도 확장으로 얹을 수는 있다. 그러나:

- 지그 생성의 핵심은 **기하 파이프라인**(build123d)이고, 그것은 부서 · 온톨로지 · 데이터 소스와
  무관하다. 틀의 대부분이 이 플랫폼에서는 지울 것이 된다.
- build123d(OpenCascade)는 배포 이미지 크기와 의존성 성격이 다르다. 틀의 이미지에 얹으면
  그 틀을 쓰는 모든 인스턴스가 OCP 를 들게 된다.
- 결과물이 파일(STEP · glTF)이라 저장소 · 뷰어가 중심이고, 틀의 「객체 · 관계」 모델과 맞지 않는다.

## 대안

1. **StandardPlatform 확장 모듈로 구현** — 로그인 · 계정 · 배포를 공짜로 얻지만, 틀이 커질 때마다
   이 플랫폼이 함께 무거워지고, 쓰지 않는 표(부서 · 온톨로지)가 DB 에 만들어진다. 기각.
2. **StandardPlatform 을 포크해서 도메인을 얹기** — 틀의 규칙(부서 스코프 · 온톨로지)을 지우면서
   시작하게 되고, 지우다 보면 공통이던 것까지 갈라진다. 기각.
3. **구조만 가져와 새로 세우기(채택)** — 필요한 것만 가져오고 코어를 중심에 둔다. 틀의 개선을
   자동으로 못 받지만, 인증 · 오류 규약은 이미 안정된 부분이라 갈라져도 비용이 작다.

## 결과

- 백엔드 모듈은 `auth` · `accounts` · `audit` · `server` · `jigs` · `cad` 여섯이고, 코어는
  `app/core` 에 따로 있다(웹 · DB 를 모른다).
- 계정은 관리자가 만든다(가입 화면 없음). 지그는 팀이 함께 보는 자료라 프로젝트는 누구나 보고,
  소유자와 시스템 관리자만 고친다.
- 포트는 8060 — 플랫폼마다 10씩 벌리는 규약을 그대로 따른다(8050 은 StandardPlatform 포트 표의
  PartTrace 예약 자리). StandardPlatform 의 표에 이 플랫폼을 한 줄 더했다.
