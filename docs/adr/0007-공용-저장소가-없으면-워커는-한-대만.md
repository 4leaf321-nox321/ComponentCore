# 0007. 공용 저장소가 없으면 작업 워커는 한 대만 — 대기(클론) 서버는 끄고, 그 값을 기억한다

날짜: 2026-10-07

## 결정

이중화에서 **두 서버가 작업물 폴더(filestore)를 함께 보지 않으면, 작업 워커와 실험계획 청소 타이머는
주 서버 한 대에서만 돈다.** 대기 서버(B)는 같은 버전 · 주 DB 를 보며 기다리는 클론이다(포탈 라우트도
주 하나).

- `deploy.sh` 가 정한다: `HA_ROLE=backup` 이고 `DATA_DIR` 가 없거나 네트워크 파일시스템(nfs · cifs …)이
  아니면 `WORKER_ENABLED=0`, 아니면 1. env 로 주면 그것이 이긴다.
- 그 값을 `/etc/platform-instances/<slug>.conf` 에 **기억한다.** `update` · `restart` 가 꺼 둔 워커를
  다시 켜지 않는다(`units_of` 가 묶음에서 뺀다).
- 유닛은 늘 깔아 둔다. 전환은 `sudo ./deploy.sh worker on|off` 한 줄 — 끄는 쪽을 먼저.
- `status` 가 「끔인데 돌고 있음」 을 ⚠ 로 말하고, `db-promote` 뒤에 남은 손일(.env · restart ·
  `worker on`)을 알려 준다.

## 배경

설계(`docs/이중화-배포-설계.md` 1장)는 두 서버가 `/data/<slug>` 를 함께 마운트하는 활성-활성이었다.
운영 서버에는 그 공용 폴더가 아직 없어, 다른 플랫폼(ReportArchive §7)과 같이 **주 하나 + 클론 하나**로
돌고 있었다. 그런데 B 의 워커는 그대로 떠 있었다. 워커는 DB 를 큐로 쓰고(ADR 0003) 호스트를 가리지
않으므로 B 의 워커도 A 의 화면에서 건 작업을 집었다(2026-10-07 운영에서 발견). 작업의 파일은 서버마다
따로라:

- A 에 올린 STEP 을 B 의 워커가 못 찾아 버전 평가 · 지그 · DOE 가 실패한다 — **B 가 집었을 때만.**
- B 가 만든 STEP · glTF 는 A 의 화면에서 「작업물 파일이 저장소에 존재하지 않습니다」 다.
- B 가 만든 실험계획 폴더 때문에 A 가 「보관 기한 경과로 정리」 를 거짓으로 띄우고, A 에 옛 사본이 있으면
  「내보내기」 가 **성공한 척 옛 설계점을 해석으로 보낸다.**

증상이 「가끔」 이라 원인에 닿기 어렵다. 조사 기록: 같은 날 두 저장소의 파일 흐름 전수(쓰는 곳 · 읽는
곳 · 프로세스) — 서버를 넘는 흐름은 전부 filestore 안이고, 요청 안의 임시 폴더는 안전했다.

## 대안

- **A 가 `DATA_DIR` 을 NFS 로 내보내고 B 가 마운트**(설계 1장의 활성-활성). 코드는 거의 그대로다. 그러나
  내보내는 A 가 죽으면 B 도 파일을 못 보고(hard 마운트면 B 의 요청이 걸린다), 포탈 라우트도 아직 주소
  하나만 받는다 — 이중화의 이득 없이 결합만 는다. 공용 저장소가 진짜 생기면(파일 서버) 이쪽으로 간다.
- **filestore 표지 검사** — 저장소에 id 파일을 두고 DB 에도 적어, 다르면 앱 · 워커가 뜨지 않는다. 한때
  만들었다가 버렸다: 클론 운영에서는 B 의 앱이 「다른 저장소」 라 아예 못 떠, 전환을 위해 대기하는 B 의
  존재 이유와 부딪친다.
- **없는 파일을 짝 서버에서 받아 오기 / 워커가 파일 있는 서버의 작업만 집기** — 앱이 스스로 이중화를
  메운다. 올린 STEP 에는 어느 서버에 있는지 적힌 곳이 없고(`artifacts` 에 호스트 없음), 실험계획 폴더는
  서버마다 다른 때의 사본이 있을 수 있어 「어느 쪽이 맞나」 를 새로 정해야 한다. 공용 저장소가 오면
  버릴 코드가 크다.
- **워커가 「DB 가 같은 서버에 있을 때만」 집기**(`inet_server_addr()` = `inet_client_addr()`) — 설정
  없이 전환을 따라가지만, DB VIP 를 받는 날 주 서버의 워커도 「원격」 으로 보여 멈춘다. 암묵이라 운영자가
  왜 안 도는지 모른다.
- **손으로만 끄기**(`systemctl disable --now`) — 지금 당장은 이것으로 막았다. 그러나 다음 `update` 가
  `setup_worker` 에서 다시 켠다. 기억해야 한다.

## 결과

- 대기 서버는 `update` 한 번으로 워커 · 청소 타이머가 꺼지고, 그 뒤로 꺼진 채로 남는다.
- 전환 절차에 한 줄이 는다 — 운영 가이드 8.1c · 8.3 · 8.4.
- 이미 B 가 집었던 작업은 한 번 되살린다: B 가 만든 `filestore/jobs` 를 A 로 rsync, 실패한 것은 다시
  걸기, 실험계획은 「재생성」(파일 단위로 섞지 않는다) — 운영 가이드 8.1c.
- 같은 함정이 같은 틀을 쓰는 다른 플랫폼(대기 서버의 워커가 주 DB 큐를 집는 곳)에도 있을 수 있다.
