# 온톨로지 이식 계획 — StandardPlatform 의 온톨로지를 들이고 SP 기준정보를 받는다

결정은 [ADR 0008](adr/0008-온톨로지와-그-기반을-StandardPlatform-에서-들인다.md). 이 문서는 **순서와
할 일**이다. 원본은 StandardPlatform `6e5a773`(v0.4.51)이고, 모듈 · 표 · 화면 경로 이름은 SP 와 같게
둔다(오류 코드 접두어만 `CCR`).

## 규모 (원본 기준, 2026-10-13 실측)

| 묶음 | 백엔드 | 프론트 |
| --- | --- | --- |
| 온톨로지 정의(`ontology`) | 11,222 줄 | 9,781 줄 |
| 객체(`objects`) | 22,958 줄 | 14,641 줄 |
| 그래프 · RDF · 찾기 | 2,099 줄 | 5,067 줄 |
| 부서 · 첨부 · 알림 · 감사 · 권한 등 기반 | 약 4,500 줄 | 약 3,600 줄 |
| 데이터 소스 · 코어 API · 묶음 · 검토함 · 웹훅 | 12,443 줄 | 4,494 줄 |
| 지표 · 분석 · 경보(`metrics`) | 6,720 줄 | 10,523 줄 |

합쳐 백엔드 약 6만 줄, 프론트 약 4만 8천 줄이다.

**백엔드는 한 묶음으로 옮긴다**(2026-10-13 실측으로 바꿈). `ontology` · `objects` 에서 import 를 따라가면
`metrics` · `review` · `bundles` · `datasources` · `coreapi` · `webhooks` · `jobs` · `workspaces` ·
`files` · `notifications` 와 shared 도우미 열여덟까지 닫힌다 — 나눠 옮기면 그 사이를 빈 껍데기로 막아야
하고, 그 껍데기가 SP 와 갈리는 첫 자리가 된다. 그래서 작업은 `feature/ontology` 갈래에서 하고,
단계(아래)는 **갈래 안의 순서**다. `main` 에는 검증을 통과한 묶음으로 들어간다.

## 단계

### A. 기반 — 부서 · 권한 · 감사 · 첨부 · 알림, 작업 큐에 「DB 작업」

온톨로지 · 객체가 기대어 서는 것. 이것만으로도 쓸모가 있다(조직도 · 알림 · 감사 기록).

- `workspaces`(부서 — 트리형 조직도, 멤버와 역할, 보관), 사용자의 `home_workspace_id` · 화면의
  「부서 전환」. 기본 부서는 만들지 않는다(ADR 0008 「지키는 것」 — 객체는 부서 관리자가 만든다).
- `shared/permissions`(시스템 역할 × 부서 역할, 부서 소유 자산 판정).
- 감사 기록 `audit_entries` + `shared/audit`(누가 무엇을 어떻게 바꿨나 — 객체 이력의 바닥).
- `files`(첨부 — 내용 해시로 중복 제거, 부서 단위 권한, 고아 정리), `notifications`(알림 벨).
- `shared` 도우미: `text` · `batches` · `sheets` · `scopes` · `system_sources` · `events`.
- **작업 큐는 둘, 워커는 하나**(ADR 0008): SP 의 작업은 `tasks`(데이터 작업, `/tasks`)로 들이고,
  워커 루프가 형상 작업이 없을 때 데이터 작업을 집는다(`worker.PlatformChores`).

### B. 온톨로지 정의

- `ontology`: 묶음(`nav_groups`) · 타입(`object_types`, `kind_class` reference · record · system) ·
  속성(`property_defs` 일곱 종류) · 관계 종류 · 인터페이스 · 코드북 · 목록 뷰 · 가져오기 · 내보내기 ·
  스냅숏 · 승격 · 종류 변경. 스키마 API `GET /api/ontology/schema`.
- 화면: 관리 › 온톨로지(묶음 · 타입 · 관계 · 인터페이스 · 가져오기 · 코어).

### C. 객체

- `objects`: 객체 CRUD · 관계 · 이력 · 별칭 · 일괄 입력(붙여넣기 · 파일, 계획 → 적용) · 첨부 · 품질 ·
  축 · 참조 색인. `graph`(트래버설) · `search`(전체 찾기).
- 화면: 사이드바의 동적 묶음, `/o/:typeSlug`(목록) · `/o/:typeSlug/:id`(상세 · 관계 · 트리 · 이력).

### D. SP 기준정보 받기 — 이 작업의 첫 목적

**SP 의 데이터 소스에 이미 있다** — 종류 `sp_core`(「형제 설치에서 코어를 당겨온다」, 시험
`test_datasource_core*.py`). 아래는 그것이 지키는 것이고, CompCore 가 더한 것은 주기 실행(타이머
`<slug>-sync.timer` · `<slug>-metrics.timer`, 운영 가이드 5e)뿐이다.

- 연결 설정(관리자): SP 주소 · `core:read` 토큰(서버에만 둔다) · 받을 타입.
- 카탈로그(`GET /core`)를 읽어 **타입 정의를 만든다**(없으면 생성, 칸이 늘면 속성 추가 — 원천이
  SP 임을 표시하고 화면에서 손으로 못 고치게).
- 증분 수신(`GET /core/<타입>` · `/relations`) — `as_of` 를 받은 그대로 저장, `next` 가 있으면
  저장하지 않음, `key` 로 갱신, `deleted` 는 비활성(`merged_into` 면 참조 이전), `hidden` 은 값을 둔 채
  비활성, `reset` 이면 그 타입을 비우고 처음부터. 끊긴 선은 지운다.
- 「DB 작업」 으로 돈다 — 수동 실행 · 타이머(기본 야간 1회) · 수신 기록(받은 수 · 지운 수 · 오류).

### E. CompCore 기능이 쓰기

- **부품 · 지그를 온톨로지의 원 표로 연다**(`system_source` `part` · `jig`) — 받은 제품 · 프로젝트가
  관계로 부품 그 자체를 가리킨다. **했다(2026-10-13).**
- **부품 · 지그 화면의 「기준정보」 칸** — 원 표 타입에 닿는 관계 종류마다 한 줄(「적용 모델」 ·
  「서비스 부품」 · 「대상 모델」 …), 칸처럼 고르고 빼고, 이름에 든 낱말로 추천한다. 잇는 사람은
  부품 주인 · 관리자. **했다(2026-10-14).** 개발 서버에는 `cc_part` · `cc_jig` 와 관계 종류
  `uses_part`(기본 모델 → 부품) · `design_part`(서비스 부품 → 부품) · `verify_jig`(기본 모델 →
  지그)를 만들어 두었다 — 운영 설치는 관리자가 같은 정의를 만든다(기본 정의 꾸러미는 다음).
- 남은 것: 목록에서 기준정보로 거르기, DOE 폴더 · 해석용 내보내기에 이은 객체의 `key` · 이름 싣기.
  작업(내 작업) · DOE 는 주인만 보는 것이라 원 표로 열지 않는다 — 잇는다면 그쪽 칸으로.
- MCP: 객체를 찾고 잇는 도구.

### F. 나머지(SP 와 거의 그대로)

데이터 소스(OData · REST · 파일), 검토함, 묶음(bundles), RDF · SPARQL, 웹훅, 지표 · 분석 · 경보,
MCP 의 온톨로지 · 객체 도구. 쓰임이 생기는 순서로 들인다.

## 원칙

- **SP 코드를 옮긴다 — 다시 쓰지 않는다.** 바꾸는 것은 이 저장소와 다른 자리(오류 접두어 · 작업 큐 ·
  설정 이름 · 화면 문구 격식체)뿐이고, 바꾼 자리에는 왜인지 적는다.
- **기존 자료의 권한 모델은 바꾸지 않는다**(ADR 0008 「지키는 것」).
- 시험도 옮긴다 — SP 의 시험이 그 모듈의 정본 동작이다.
