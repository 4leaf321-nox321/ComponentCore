# 오케스트레이터가 지휘하는 흐름 — 폴더의 수명과 빠진 자리

> 작성 2026-09-24. 지금까지의 DOE 는 **사람이 화면에서 누르는 것**을 전제로 만들어졌다.
> 오케스트레이터(기계)가 CAD 를 보고 DOE 를 만들고 해석까지 이어 거는 그림이 오면 무엇이
> 부족한지, 그리고 **공유 폴더가 쌓이는 문제**를 어떻게 다룰지 정한다.

## 0. 그림

```
오케스트레이터
  ① CAD 를 본다      ──MCP──▶ CompCore   search · work_geometry · recipe_find …  (있다)
  ② DOE 를 만든다    ──MCP──▶ CompCore   doe_preview · doe_create               (있다)
  ③ 끝났나           ──MCP──▶ CompCore   doe_status · doe_wait                   (있다)
  ④ 내보낸다         ──MCP──▶ CompCore   doe_export → 폴더 경로                 (있다)
  ⑤ 해석을 건다      ──MCP──▶ SimEngBay  (그쪽 일)
  ⑥ 결과를 본다              SimEngBay 화면 — **우리에게 돌아오지 않는다**(결정)
  ⑦ 다 썼다          ──MCP──▶ CompCore   doe_release → 폴더를 먼저 치운다       (있다)

  ①~④ 를 한 번에:            ──MCP──▶ CompCore   doe_run(만들고 · 기다리고 · 내보낸다)
```

**경계 한 줄: 데이터는 폴더로, 명령과 상태는 MCP 로.** 폴더에 상태를 적어 조정하지 않는다
(마커 파일 · 완료 표시). 두 곳에 상태가 있으면 어긋나는 날 **진실이 둘**이 된다.

## 1. 폴더가 쌓이는 문제 — 잰 값부터

```
설계점 한 점 = STEP 33 KB + 점 파일 ~3 KB ≈ 36 KB   (둘을 합치기 전에는 파일이 셋이었다)
   48점 →    96 파일 ·  1.7 MB        200점 →   400 파일 ·  7.1 MB
 1000점 → 2,000 파일 · 35.5 MB
```

**용량은 문제가 아니다.** 하루 10 스터디 × 200점이면 6,000 파일 · 70 MB/일 — 디스크는 견디지만
**폴더는 못 견딘다**(백업 스캔 · 탐색기 · 「이 폴더가 무엇이었나」).

### ① 폴더는 둘이고, **정본은 어느 쪽도 아니다**

| | 서버 보관 폴더 | 공유 폴더 |
| --- | --- | --- |
| 어디 | `filestore/doe/<이름>-<id8>/` | `DOE_EXPORT_ROOT/<이름>-<id8>/` |
| 누가 만드나 | DOE 작업이 여기에 **직접 쓴다** | 「보내기」 가 위를 **복사**한다 |
| 누가 읽나 | CompCore(내려받기 · 복사원) | 해석 플랫폼 |
| 수명 | 180일(기본) | 30일(기본) · 「다 읽었다」 면 즉시 |

**정본은 DB 의 스냅샷**(레시피 + 인자 + 시드 + 조건)이고 두 폴더는 **둘 다 그것에서 나온
것**이다. 그래서 어느 쪽을 지워도 잃는 것은 **다시 만드는 시간뿐**이다 — 운영 가이드가
「백업 대상이 아니다」 라고 적어 둔 까닭이고, 그러면 **수명이 있어야 앞뒤가 맞는다.**

되살리는 길이 **먼저** 있어야 지우는 것이 안전하다 — 그것이 `doe_rerun` 이다(2026-09-24).
없는 채로 서버 보관 폴더를 지우면 「보내기」 가 영영 막힌다.

### ② 수명은 둘로 막는다 — 다 썼다는 신호 + 시간

| | 무엇 | 왜 셋 다 |
| --- | --- | --- |
| `doe_release(study_id)` | 오케스트레이터가 「다 읽었다」 | 지휘자가 아는 것을 말해 주는 것이 가장 정확하다 |
| 보관 기한(**기본 30일**) | 아무도 말 안 해도 지운다 | 오케스트레이터가 죽거나 사람이 손으로 돌렸을 때 |
| **영구보관**(스터디마다) | 기한이 지나도 남긴다 | **지우는 일은 되돌릴 수 없다.** 「이건 남겨야 한다」 를 아는 사람이 그때 켠다 — 기한은 기본값이고 예외가 규칙보다 세다 |

**다시 보내면 「다 읽었다」 는 무효다.** 안 그러면 방금 보낸 폴더가 다음 청소에 곧바로
치워진다 — 해석이 아직 열어 보지도 않았는데(시험이 잡았다).

**서버 보관 폴더도 같은 셋으로 막되 한 단계 더 조심한다**(2026-09-24). 여기가 복사원이라
지우면 「보내기」 가 곧바로 막히므로, **아직 공유 폴더에 나가 있으면 건드리지 않는다**
(`export_dir` 이 차 있으면 건너뛴다). 공유 폴더 청소가 먼저 돌아 그 칸을 비우면 그때 차례가
온다 — 그래서 청소 스크립트도 그 순서로 돈다. 영구보관은 **두 폴더에 똑같이** 걸린다: 한쪽만
켜게 하면 나머지가 조용히 사라지는 날이 온다.

지우는 것은 **파일뿐**이다. DB 의 스터디 · 설계점 · 스냅샷은 남으므로 화면은 그대로 뜨고
(표는 DB 에서, 3D 는 레시피로 다시 만든다), 「다시 만들기」 가 같은 파일을 되살린다.
청소는 매일 도는 systemd 타이머(`<slug>-cleanup.timer` → `scripts/cleanup_doe_exports.py`)다 —
백업(03:00)이 끝난 04:10 에, 지워질 폴더도 그날 백업에는 한 번 들어가게.

**스터디를 지울 때는 다르다.** 그때는 서버 보관 폴더를 **함께 지우고**(우리 것이고, 줄이
사라지면 아무도 못 찾는 쓰레기가 된다) 공유 폴더의 사본은 **남긴다**(해석이 제 결과를 덧붙여
두었을 수 있다).

### ③ 파일 개수 자체를 줄인다

- ✅ **점 파일 둘을 하나로**(2026-09-24). `pNNNN.topology.json` + `pNNNN.conditions.json` →
  `pNNNN.json`(안에 `point` · `bodies` · `regions` · `conditions`). 3N → 2N 이고, 받는 쪽이
  짝을 맞춰 읽을 파일도 하나 줄었다.
- **같은 형상은 한 번만 쓴다.** 조건만 훑으면(압력 2 · 3 MPa) STEP 이 전부 같다. `recipe_digest`
  가 같으면 `shapes/<digest>.step` 하나를 쓰고 점 파일이 그것을 가리킨다. 조건 훑기에서 파일과
  용량이 **N 배** 줄고, 받는 쪽은 「같은 메시를 다시 쓸 수 있다」 를 그 자리에서 안다.

## 2. 기계가 지휘하려면 빠진 것

### ⓪ 같은 스터디를 **다시 돌리는** 길 ✅

`doe_rerun(study_id, only="all"|"failed")` (2026-09-24). 스냅샷으로 설계점 파일을 되살린다 —
**새 스터디가 아니라 같은 스터디**이고 같은 재료라 같은 것이 나온다. 기계는 두 자리에서 이걸
쓴다: 보관 기한이 지나 `doe_points` 의 `files_ready` 가 False 일 때(그 상태로는 `doe_export`
가 막힌다), 그리고 실패한 점만 한 번 더 해 볼 때.

**다시 만드는 것이 STEP 을 읽는 것보다 빠르지는 않다** — 구멍 24 짜리 판에서 만들기 257 ms
대 읽기 28 ms 이고, 연산이 많을수록 벌어진다. 그런데도 이 길이 정본인 까닭은 **읽을 STEP 이
없을 수도 있기 때문**이다. 화면의 3D 도 같은 이유로 늘 레시피에서 만든다(`point_mesh`).

### ① 끝날 때까지 기다려 주는 도구

`doe_create` 는 작업을 걸고 **즉시** 돌아온다(화면이 폴링하는 전제). 오케스트레이터는 폴링
루프를 제 쪽에 만들어야 하는데, 우리는 이미 `run_jig` 에서 **기다렸다 돌려주는** 모양을 쓴다.

    doe_run(work_id, factors, …) → 만들고 · 기다리고 · 내보내고 → {folder, points, failed}

한 번 부르면 다음 단계(SimEngBay 호출)로 갈 수 있는 것이 기계에게 맞다.

### ② 누구의 자격으로 부르나 — **여기서 가시성 결정이 강제된다**

오케스트레이터는 사람이 아니다 → PAT(서비스 계정). 그러면 그 DOE 의 소유자가 서비스 계정이
되고, 지금처럼 **개인 전용**이면 정작 사람이 못 본다(목록에 안 뜨고 403). 셋 중 하나를 골라야
한다:

| | 뜻 |
| --- | --- |
| **대행**(`on_behalf_of`) | 오케스트레이터가 「누구를 위해」 만드는지 밝히고 소유자를 그 사람으로 |
| **읽기 공개** | 소유자는 서비스 계정, 나머지는 본다 |
| **작업공간 소유** | 부서가 갖는다 |

**대행 + 읽기 공개**가 맞다고 본다 — 만든 책임은 사람에게, 보는 것은 모두에게.

### ③ 두 번 불러도 한 벌 — 멱등성

기계는 재시도한다. 같은 요청이 스터디 둘 · 폴더 둘을 만들면 해석 쪽은 **어느 것이 진짜인지
모른다**. `idempotency_key`(없으면 레시피 · 인자 · 시드의 다이제스트)로 **이미 있는 것을 돌려
준다.** 이것은 「만들기」 뿐 아니라 「보내기」 에도 있어야 한다.

### ④ 상태를 묻는 자리

`doe_status(study_id)` — 만드는 중 · 끝 · 몇 점 실패 · 폴더 경로(서버 경로와 해석이 여는
경로 둘 다). 지금은 `doe_points` 가 표 전체를 준다 — 기계가 진행만 보려고 200줄을 받는다.

### ⑤ 폴더가 자기를 말하게 — 누가 만들었나

`study.json` 에 **만든 사람**이 없다. 오케스트레이터가 만들면 더 필요하다 — 「이 폴더가
무엇이고 누가 시켰나」 를 폴더만 보고 알아야 한다(자기 설명적 원칙). `owner` ·
`requested_by`(대행이면 사람) · `created_at` 을 싣는다.

**여섯 다 됐다(2026-09-24).** 기계가 지휘하는 데 빠진 자리는 이제 없다.

정한 것과 **문서와 달라진 것**:

- **멱등 열쇠를 우리가 지어 내지 않는다.** 이 문서는 「없으면 레시피 · 인자 · 시드의
  다이제스트」 라고 적었는데, 그러면 사람이 **같은 설정으로 한 벌 더** 만드는 정상적인 일이
  막힌다(비교하려고 두 번 돌리는 것은 흔하다). 열쇠를 안 주는 것이 곧 「멱등하지 않다」 는
  뜻이고, 그것이 사람의 기본값이다. 기계는 늘 준다.
- **대행 자격은 사람이 아니라 토큰에 붙인다**(`act_for_others` 범위). 시스템 관리자로
  게이트하면 오케스트레이터 계정이 관리자여야 하는데, 그것은 과한 권한이다.
- **읽기 공개는 있던 줄에도 걸었다.** 새것만 공개하면 정작 쌓여 있는 이력이 안 보여서 이
  변경이 누구에게도 도움이 안 된다. 감추는 것은 소유자가 하나씩 돌린다.
- **겹침 제거는 바이트가 아니라 레시피로 잰다.** 같은 형상을 두 번 써도 OCC 의 일련번호
  때문에 STEP 바이트가 달라진다(실측). 식을 다 푼 노드의 지문이라 **만들기 전에** 알고,
  그래서 조건 훑기가 형상을 아예 한 번만 만든다.

## 4. 아직 안 정한 것

- **오케스트레이터는 AI 다**(2026-09-24 확인) — local LLM 이 우리 PAT 을 들고 MCP 로 붙는다.
  그래도 MCP 에만 있는 편의(기다려 주는 도구 등)는 **API 에도** 둔다 — MCP 는 그것을 감싸는
  얇은 층이어야 하고, 그래야 AI 가 아닌 것이 붙는 날 다시 만들지 않는다.
  **지켰다**: `doe_run` · `doe_status` · `doe_wait` · `doe_rerun` 은 모두 HTTP 엔드포인트가
  먼저 있고 MCP 는 그것을 부른다. 공개 API 문서(`docs/공개-API.md`)가 그 목록이다.
- **해석이 실패했을 때 폴더를 지워도 되나** — 다시 돌릴 수 있어야 하므로 `release` 는 「성공」이
  아니라 「더 안 읽는다」 는 뜻이어야 한다.
